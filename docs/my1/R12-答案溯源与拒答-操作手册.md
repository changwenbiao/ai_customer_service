## 第一篇 · 需求与背景

### 1.1 一句话说清这个需求

让 Agent 的回答做到**每条事实都可溯源**，资料不足时**敢于拒答**——把"幻觉治理"从"只改 prompt"变成"检索侧锚点 + 程序侧校验 + 前端可查"的三层闭环。

它解决 R11 没解决的核心问题：

> R11 把"该去哪篇文档"的路由做好了，但用户得到的仍是一段**裸文本回答**——既不知道模型有没有真用到检索结果，也无法判断哪些事实是原文、哪些是模型自己编的。

### 1.2 业务代价：幻觉比答不上来危险 10 倍

电商客服幻觉的真实代价不是"体验差一点"，而是以下四类**可量化的业务后果**：

| 幻觉类型 | 典型场景 | 业务后果 | 单次代价估算 |
|---|---|---|---|
| **金额错误** | "运费平台承担"（实际买家承担） | 赔付、补贴 | 单笔 50~5000 元 |
| **时效错误** | "30 天无理由"（实际 7 天） | 超期退款 | 单笔 200~2000 元 |
| **责任认定错误** | "质量问题卖家全责"（实际过保） | 纠纷、投诉 | 工单成本 50+ 元 |
| **合规风险** | "72 小时内可退换任何商品" | 违反消保法 | 监管处罚 10⁴~10⁵ 元 |

> 经验数据：**可量化事实（金额/时效/比例/责任）占投诉的 60%+**（Synthara 2026 企业 RAG 调研）。纯文案类幻觉（"您好，我们很重视您的反馈"）几乎不会触发投诉。所以 R12 不追求"消除所有幻觉"，而是**消灭可量化事实错误 + 让其余幻觉可追溯可拒答**。

反过来，"答不上来"的代价是：
- 用户转人工（增加 1 个工单，成本 ~5 元）；
- 轻度体验下降，但不会产生错误承诺。

所以 R12 的核心观点：**拒答不是体验问题，是风控问题。宁可多拒答，不可多泄漏。**

### 1.3 技术背景：改造前 → 改造后

| 环节 | 改造前 | 改造后 |
|---|---|---|
| `search_kb` 返回 | `- 纯文本拼接` | `[n] 编号文本 + ContextVar citations` |
| Prompt | 无引用约束 | "每个结论后标 [n]；资料不足说不知道" |
| 生成后校验 | 无 | 正则 `[n] ⊆ citations`，非法 → 拒答 |
| Go 透传 | 只推纯文本 | SSE end 携带 `citations[]` |
| 落库 | `messages.content` 纯文本 | `messages.metadata` 存 citations |
| 前端 | 只渲染 AI 回复 | 可折叠"参考来源"，点击展开原文 |
| 数字事实 | 模型凭记忆答 | 强制走 `query_order` / 政策表 |
| 高风险 | 全进主链路 | 3 次采样比对，分歧大降级拒答 |

### 1.4 需求定义：做什么、不做什么

**做（In Scope）**

1. 检索结果结构化（`[n]` 编号 + ContextVar 持有 citations）；
2. 强制引用 Prompt（system prompt + 工具描述同步）；
3. 后置引用校验（正则 `[n] ⊆ citations`，非法 → 拒答）；
4. Go 侧 citations 透传与落库；
5. 前端参考来源展示；
6. 数字类事实校验；
7. 高风险问题自一致性（加分）；
8. 评测扩展：citation 覆盖率、拒答率、泄漏率、Faithfulness（LLM-as-judge）。

**不做（Out of Scope）**

| 不做的事 | 归属 |
|---|---|
| 语义意图分类器 | 4.7 的 L1 只做 dense 分数闸门，不做意图分类模型（需要标注、成本高），留给后续扩展 |
| Prompt 版本门禁、灰度、回滚 | R16 |
| 训练 abstention token / refusal SFT | 模型训练侧改动太大，本项目只用 prompt + 程序侧 |
| 复杂 claim-level 校验（NLI、STS） | 成本太高；本项目用正则 `[n] ⊆ citations` + 数字事实覆盖 |
| 多轮摘要注入、槽位持久化 | R13 |
| 完整 LLM-as-judge 评估流水线 | R12 第八章给工具，R16 做门禁 |

### 1.5 七个步骤 → 四道闸门

本项目把七步收敛成**四道闸门**（详细映射见 [3.1](#31-四道闸门总览先看这两张表)）：

```text
检索结果 → 组装 prompt → 生成 → 校验 → 返回 / 拒答
   │            │          │
   │            │          └─ 闸门三：事实对不对（数字/实体校验，可选）
   │            └─ 闸门二：有没有依据（[n] 编号 + 强制引用 + 后置校验）
   └─ 闸门一：能不能答（L2 阈值兜底 / L1 前置闸门，默认只开 L2）

闸门四：兜不兜得住（拒答话术 + citations 落库 + 前端可查 + 自一致性抽检）
```

> 为什么**不能只改 prompt**？Prompt 不是 100% 可靠——模型偶尔会漏标 `[n]`、或编造不存在的 `[9]`。闸门二的程序侧校验才是硬闸门。

### 1.7 验收标准（可量化）

| 验收项 | 目标 | 怎么测 |
|---|---|---|
| 无答案拒答率 | ≥90%（15 条里 ≤1 条泄漏） | 用 R11 评测集的 15 条无答案题跑 |
| 有答案引用覆盖率 | 100%（每条结论都有合法 `[n]`） | 人工抽样 20 条，正则 `[n] ⊆ citations` |
| 事实错误率 | 从基线下降到个位数 | 同 20 条抽样，核对金额/时效/责任 |
| 前端可查 | 点开参考来源能看到原文片段 | 手点验证 |
| 不引入回退 | 拒答策略不能让有答案问题准确率显著下降 | 对比基线答案命中率 |

> **不能只看"拒答率 ≥ 90%"**——必须同时看**误拒率**（有答案被拒的比例）。经验值：误拒率 ≤ 5% 可接受，>10% 说明策略太激进。

## 第二篇 · 原理总览

> 面试能拉开差距的，是"我知道 citation 为什么能解决 grounding、三类拒答策略各自的代价是什么、为什么阈值不能单独拒答、为什么引用校验不能只靠 prompt"。
> 每个原理都对标到本项目的 Step。

### 2.1 RAG 幻觉的本质

**幻觉（Hallucination）** 是模型生成"听起来合理但不真实"内容的统称。在 RAG 链路下，幻觉有三种完全不同的成因：

| 类型 | 成因 | 例子 | 对应 Step |
|---|---|---|---|
| **检索未召回** | 正确段落没进 top-k | 问题被召回到无关文档，模型基于"正确格式"编造答案 | R11 解决 |
| **生成未 grounded** | 正确段落进了 prompt，但模型没用到或理解错 | prompt 里有"运费买家承担"，模型答"平台承担" | Step 1+2+5 |
| **引用幻觉** | 模型编造不存在的 `[9]` 或引用了不属于这道题的 chunk | 回答里出现 `[9]`，但 citations 列表里只有 3 条 | Step 5 解决 |

R12 主要解决后两类，同时通过 Step 5 的校验反过来暴露第一类（没检索到 → 没引用 → 被拒答）。

### 2.2 Grounding 机制的本质：从"让模型记住"到"让模型引用编号"

**不用 citation 的 RAG**：

```
prompt: "根据资料回答问题。"
资料: [几段文本]
问题: "退货运费谁承担？"
回答: "退货运费由买家承担。"   ← 对，但是怎么来的？不知道
```

- 模型"应该"从资料里找答案，但没有机制保证它**真的**用了；
- 模型如果凭参数记忆答了一样的内容，用户和程序都无法区分。

**用 citation 的 RAG（Step 1+2）**：

```
prompt: "每个结论后标 [n]，只能引用给的编号；资料不足说不知道。"
资料: "[1] 退货运费由买家承担。\n[2] ..."
问题: "退货运费谁承担？"
回答: "退货运费由买家承担。[1]"
citations (ContextVar): [{"index":1,"doc_id":"...","title":"退..."}]
```

**关键变化**：
1. 回答里的 `[1]` 是**程序分配的编号**，不是模型编造的——程序持有编号 → chunk 的权威映射；
2. Step 5 可以做机械校验：`[1] ∈ {1,2,3}` 成立、且引用的 chunk 确实包含"退货运费由买家承担"——第二步校验可以留到 LLM-as-judge 或离线评估；
3. 前端、落库、审计都能从 `[1]` 反查到原文。

> 这就是 citation 机制的数学本质：**把 grounding 从"模型的软承诺"变成"编号的硬契约"**。

### 2.3 为什么 Prompt 不是可靠的硬闸门

Prompt 是**行为约束**，不是**行为保证**。两个原因：

1. **模型训练目标与目标不一致**：LLM 的训练目标是"预测下一个最可能的 token"，不是"严格遵循用户指令"。Prompt 约束能提升"遵循概率"，但永远有漏网。
2. **Prompt 是单轮上下文的一部分**：上下文里同时有 system prompt、历史对话、检索资料，prompt 约束会被"稀释"。资料里有"买家承担运费"、历史对话里客服曾说过"平台承担运费"、用户问题是"运费谁承担"——模型在多个信号中权衡，约束可能被其他信号盖过。

**CiteGuard-RAG（智源，2026）** 的消融实验直接证明了这一点：

> 移除后置验证模块后，即使检索准确率保持 99.1%，答案依据准确率（grounded-answer accuracy）**从 98.3% 暴跌到 ~70%**——证明"检索好 + prompt 约束 ≠ grounded 生成"，后置验证是必要环节。

### 2.4 三类拒答（abstention）策略

R11 证明了"单靠阈值"不可靠，拒答必须分层叠加。三类策略对应不同成本、不同防线位置：

| 策略 | 防线位置 | 机制 | 本项目实现 | 成本 | 误拒风险 | 漏网风险 |
|---|---|---|---|---|---|---|
| **L1 前置意图闸门** | 检索前 | dense top-1 < 阈值 → 直接拒答，**不调用模型**；寒暄/订单/工单放行 | 已实现（`ENABLE_PRE_RETRIEVAL_GATE`，默认关闭） | 低（多一次 dense 检索） | 中等（分数重叠，见 4.7） | 中（只拦明显越界） |
| **L2 检索阈值兜底** | 检索后、进模型前 | `Top-1 score < t → 拒答` | 已实现（`RETRIEVAL_SCORE_THRESHOLD`） | 零 | 中等（R11 已证明） | 高（分布重叠） |
| **L3 生成后引用校验** | 生成完、返回前 | 正则 `[n] ⊆ citations`，非法 → 拒答 | Step 5 实现 | 低（正则 + 替换） | 低 | 中（claim 匹配不充分） |

**本项目选择的策略组合**：
- L1：已实现 dense 分数闸门但默认关闭（4.7），只在"越界问题多、KB 覆盖范围明确"时开启；
- L2：低分阈值做兜底（`RETRIEVAL_SCORE_THRESHOLD` 生效）；
- L3：**主力拒答策略**，因为 R11 已证明分布重叠，阈值只能兜极端低分；
- **总防线**：`L2 兜底 → 模型生成 → L3 硬校验 → 非法则拒答 → 合法 + 可展示 citations`。

> EverydayGPT（2026 Confidence-Gated Routing）把这个建模成三选一路由：`π(q, D) → {RAG, GPT, REFUSE}`，核心思想是"拒答也是一种生成策略，而不是异常处理"。

### 2.5 引用校验的数学模型

**Step 5 的正则校验**（必要条件）：

```python
cited_ids = set(re.findall(r'\[(\d+)\]', answer))  # 提取回答里所有 [n]
valid_ids = {c['index'] for c in citations}          # 程序持有的合法编号
if not cited_ids.issubset(valid_ids) or not cited_ids:
    # 拒答
```

- **必要不充分**：保证"回答里引用的编号都是真实存在的"，但不保证"编号对应的 chunk 真的支持被引用的 claim"。
- 充分条件的近似可以加一层 LLM-as-judge（本项目第八章给了工具，R16 做门禁），但**正则校验是零成本、100% 可靠的硬闸门**，必须先做。

**拒答话术的约束**：拒答不能包含任何臆造事实。所以替换的拒答文案必须是**固定模板**，不能让模型生成。例如：

> "抱歉，关于您的问题我暂时没有查到准确信息，建议您稍后重试或联系人工客服（客服热线 400-XXX-XXXX）。"

### 2.6 数字类事实为什么要单独校验

Synthara 2026 调研显示：

> 可量化事实（金额/时效/比例/数量/截止日期/责任主体）占**客服幻觉投诉的 60%+**。

原因是：
1. **可量化事实是高频高风险领域**——运费、退款金额、时效、保修条款，用户一搜就能核实；
2. **模型对数字的"精确性"天生较弱**——它学到的是"X 天"、"X 元"的语义，不是精确值；
3. **纯 prompt 约束对数字无效**——prompt 说"数字必须来自资料"，模型还是可能把"7 天"说成"30 天"。

本项目 Step 6 的做法（和 RAGShield / Reverify MCP 同思路）：
1. 在 prompt 里标注"金额/时效/比例必须从工具查询结果或资料里**逐字引用**"；
2. 后置 guard 检测回答里的数字 claim（`\d+(\.\d+)?[元%天小时月]`），和引用 chunk 里的数字做匹配；
3. 不匹配 → 降级为拒答 / 引导查订单。

### 2.7 自一致性（Self-Consistency）

**原理**：对同一问题采样 N 次（N=3），如果生成答案分歧大 → 说明这条知识"不够确定"，降级为拒答。

**适用条件**（必须满足，否则浪费钱）：
- 采样成本可控（本项目的 100 条离线评测适合，线上主链路不适合）；
- 问题有明确的"有 / 无答案"分桶（无答案问题如果 3 次都拒答 → 置信度高；如果有的拒答有的瞎答 → 置信度低）。

**成本**：3× LLM 调用，延迟也 3×。
**边际收益**：对线上主链路是 5-10%（因为 L3 引用校验已经解决了大部分幻觉）；对离线评测的风险评估有用。

**建议**：本项目 Step 7 作为加分项离线抽检使用。线上主链路靠 Step 5+6 就够。

### 2.8 流式与非流式下的差异

| 模式 | 正文推送 | citations 下发 | 校验时机 | 校验失败处理 |
|---|---|---|---|---|
| **非流式** | 完整 `content` 一次返回 | 同 payload（或无单独字段） | 返回前 | 完整替换成拒答，一次返回 |
| **流式** | `content` chunk 持续推送 | `end` 事件携带 | `end` 事件到达时 | 已推出去的内容无法撤回；两种方案：(a) 完整拼完再推（延迟 ↑）；(b) end 推"更正提示"追加在消息末尾 |

**本项目选择**：流式用方案 (b)——用户先看到内容，`end` 时如果校验失败，用特殊 `content_type="notice"` 推一条拒答 / 更正消息。

### 2.9 RAGAS 指标 → 本项目指标映射

R12 第八章给了评测脚本的扩展方向，核心是把 RAGAS 的标准化指标映射到本项目的实际场景：

| RAGAS 指标 | 定义 | 本项目对应指标 | 说明 |
|---|---|---|---|
| **Faithfulness** | 回答是否**完全**由引用 chunk 支持（0=不支持，0.5=部分支持，1=完全支持） | 回答里出现"资料不足" / 无引用 / 有非法引用 → 0；引用合法且数字校验通过 → 1 | 最核心的 grounding 指标，LLM-as-judge 计算 |
| **Answer Correctness** | 回答与 reference 的语义相似度 | R11 的 `must_contain` 扩展到语义包含（关键词 → LLM-as-judge） | |
| **Context Recall** | 相关 claim 是否都被检索到 | R11 的 `Recall@k` / `Evidence hit@k` | |
| **Context Precision** | 检索到的 chunk 中相关 claim 比例 | R11 没单独算，但重排后会自然提升 | |
| **Answer Relevance** | 回答是否真的回答了用户问题 | LLM-as-judge 或关键词匹配 | |
| **Citation Precision** | 回答里引用的 chunk 是否真的被使用 | 正则校验 + LLM-as-judge 判定引用是否相关 | 本项目 Step 5 保证下限 |
| **Citation Recall** | 回答里应该引用的 chunk 实际引用了多少 | 人工标注 + LLM-as-judge | |

### 2.10 7-Layer Defense（Synthara 2026 经验）

Synthara 的企业 RAG 调研显示：**每层通常消除前一层 40-70% 的残差错误**。R12 覆盖了后三层：

```
Layer 1: Query rewriting         ← R13 的上下文工程可以辅助
Layer 2: Hybrid retrieval        ← R11 做了 BM25 + dense + RRF
Layer 3: Reranking               ← R11 做了 bge-reranker-v2-m3
Layer 4: Evidence sufficiency    ← R11 阈值扫描（但证明不够）
Layer 5: Grounded generation     ← R12 Step 1+2 强制引用
Layer 6: Post-generation verify  ← R12 Step 5 引用校验
Layer 7: Continuous evaluation   ← R16 做门禁回归
```

**关键启示**：R12 是 Layer 5+6，**必须叠在 R11 的 Layer 2+3 之上**——检索召回不好，grounding 校验就没东西可校验。

### 2.11 Benchmark 的局限（HaluEval 被启发式破）

2026 年的 HalluLens 论文指出：最广泛使用的 HaluEval benchmark **可以被一个启发式破——"回答长度 > 27 字符"就能达到 93.3% 准确率**。这说明：

1. **合成 benchmark 可能被最简单的规则刷爆**；
2. 本项目用 R11 的**真实问法分桶（有答案/无答案）** 更接近线上分布；
3. 所以"benchmark 高分"不应作为最终验收，验收必须看**线上 bad case 和人工抽样**。

### 2.12 本项目指标 vs 线上系统典型口径

| 维度 | 本项目值（线上典型值） | 差异说明 |

### 0.1.0 为什么 1+2 之后先做 5，跳过 3+4

直觉上"做完 1+2 应该做 3+4 把引用展示出来"，但**先做 5 更划算**，三个理由：

**理由一：Step 5 能立刻上线、立刻见效、立刻压幻觉**

Step 5 的核心是"回答生成完之后，程序检查回答里有没有引用、引用编号合不合法——不合法就直接替换成拒答话术"。这个逻辑**全部在 Python Agent 侧完成**，不需要 Go 改接口、不需要前端改页面、不需要 DDL 加列。代码就是 main.py 里加一个 `citation_guard()` 函数，在流式 `end` 之前、非流式 return 之前调一下。改完重启 Agent 就生效。

Step 3（Go 透传）和 Step 4（前端展示）是**体验增强**——让用户能看到"参考来源"。但引用本身能不能压住幻觉，不取决于用户看得到看不到，而取决于**程序有没有在模型回答完之后做校验**。Step 5 不做，模型就是不标 `[n]` 或者编个 `[9]`，用户也看不出来；Step 5 做了，不管前端展不展示，幻觉已经被替换成拒答了。

**理由二：Step 5 校验通过 = Step 3+4 有内容可展示**

如果先做 3+4 让前端能渲染 citations，但 Step 5 还没做，会出现：
- 模型偶尔不标 `[n]`（prompt 约束不是 100% 可靠）→ 前端渲染"参考来源（3）"但正文一个引用都没有 → 用户困惑
- 模型编了不存在的 `[9]` → 前端渲染来源但对不上 → 更糟

Step 5 先把这两种情况挡住——citations 为空或不合法时直接替换成拒答，那前端永远不会遇到"有来源但正文没标"或"标了不存在的号"的尴尬。

**理由三：Step 5 的效果能立刻验证，反过来指导 Step 6 的阈值**

Step 5 做完，你可以马上拿 R11 评测集跑一遍：多少有答案问题模型没标引用？多少无答案问题模型还在瞎编？这些数字直接告诉你 prompt 够不够强、阈值要不要调——而 Step 3+4 做完了也拿不到这些数据，因为没校验、没拒答，幻觉回答原样返回，你看不出 baseline 到底有多糟。

**总结**：

```
Step 1+2 做完 → 模型"能标引用"（但不一定标、也可能编造）
    → Step 5 做完 → 程序"强制校验引用"（不合法直接拒答）→ 幻觉压下去了、能量化效果了
        → Step 3+4 做完 → 用户"能看到引用来源"（体验闭环）
```

顺序反了（1+2 → 3+4 → 5）会出现：引用展示有了，但偶尔出现"有来源没标引用"的奇怪态；而且 Step 5 的验收数字也拿不到 baseline——因为幻觉回答已经被前端展示出去了，你没法量化"拒答率"和"泄漏率"。

### 0.1.1 Step 1 与 Step 2 的关系（必须一起做，缺一不可）

| 维度 | Step 1（检索结果结构化） | Step 2（强制引用 Prompt） |
|---|---|---|
| **改哪一层** | 工具层（search_kb 返回格式） | Prompt 层（system prompt 文本） |
| **给模型的** | `[n] 编号文本`（工具返回值里自带编号） | "必须用 [n] 标注、禁止编造"（行为约束） |
| **给程序的** | ContextVar 里的结构化 citations 列表 | 无（prompt 是给模型看的） |
| **单独做会怎样** | 模型看到编号但**可能不标、可能编造**（没有约束它）——citations 拿得到，但回答里没引用 → Step 5 的校验也通不过 | prompt 约束模型"必须用 [n]"但 search_kb 返回的是 `- 纯文本`——模型想标也没编号可用 → 引用形同虚设 |
| **一起做的效果** | 模型**能看到编号 + 被 prompt 逼着用编号** → 回答里出现有效 `[n]`；程序能拿到 citations 做校验/落库/展示 |

**一句话**：Step 1 造编号（让模型有得标）、Step 2 逼模型标编号（让模型真去标），两者配合才产生"回答里有引用"。

另外一个必须知道的事实：**Prompt 是 DB 驱动的**——config.py 里的 `DEFAULT_SYSTEM_PROMPT` 只在 DB `prompts` 表为空时作为 seed 写入，之后租户级 Prompt（`is_active=1, tenant_id=''`）优先。所以 Step 2 代码改完后，如果 DB 里已有活跃 Prompt，需要用 SQL 手动 update（见 5.2.3 节），否则租户级 Prompt 仍会覆盖默认值。

### 0.3 术语对齐（面试也会问）

- **有据生成（grounding）**：回答的事实来自检索到的原文，而不是模型参数记忆；量化指标是 RAGAS 的 Faithfulness。
- **引用（citation）**：正文里的 `[n]` 与程序维护的来源列表一一对应，编号可校验；它是实现"溯源"的手段，不等于"有依据"。
- **拒答（abstention）**：资料不足时明确说"不知道 / 查不到"，并引导转人工。
- **引用校验（citation guard）**：判断"回答里的 `[n]` 是否合法、对应片段是否支持该 claim"，不是判断"回答对不对"。
- 完整术语对照见 [R11 附录 F 统一术语表](file:///Users/changwenbiao/PycharmProjects/ai_customer_service/docs/my1/R11-RAG评测与召回优化-操作手册.md#L2441-L2477)。

### 3.1 四道闸门总览（先看这两张表）

R11 是一条线性链路（召回→融合→重排→截断），所以章节能按 Step 1~5 排；R12 是**横切在生成侧的防线**，多层措施可以互相替代，如果按"步骤"排就会显得零碎。四道闸门的组织方式是：**先按失败模式分组，再在组内选措施**。

## 第四章 · 闸门一：能不能答

### 4.1 这道闸门解决什么

- **L2 阈值兜底**（默认开启）：`search_kb` 内部过滤低分 chunk，模型看到"未找到相关信息"，按 prompt 拒答。
- **L1 前置闸门**（默认关闭）：进入模型前 dense top-1 低于阈值，直接拒答，不调用模型。

两者的选择标准：**误拒代价高就只开 L2；越界问题多、且知识库覆盖范围明确，再开 L1**。

### 4.2 先承认 R11 的数据结论

- 无答案问题的 dense 相似度中位数约 0.547，而有答案问题的最低分约 0.497 —— **分布重叠**；
- 也就是说：**任何单一阈值都无法同时做到"不误拒"和"不泄漏"**；
- 不同模式分数量纲不同（dense 0.5~0.8 / RRF 0.5~1.0 / rerank 对数似然可负），阈值不能跨模式复用。

所以 R12 的拒答要分三层，阈值只作为辅助。

### 4.3 三层策略与取舍

| 层级 | 触发条件 | 动作 | 强度 |
| --- | --- | --- | --- |
| L1 前置意图闸门 | 进入模型前，dense top-1 < 阈值（寒暄/订单/工单放行） | 直接返回拒答话术，**不调用模型**（`ENABLE_PRE_RETRIEVAL_GATE`，默认关闭） | 强（可选，见 4.7） |
| L2 检索阈值兜底 | `search_kb` 内过滤后 0 条 / top1 低于阈值 | chunk 被滤掉，模型看到"未找到相关信息"，据 prompt 拒答 | 中 |
| L3 无引用/引用非法 | 模型有资料却一个 `[n]` 都没标，或标了不存在的编号 | 用拒答话术替换回答，并记日志 | 强（推荐主策略） |

**推荐主策略是 L3**：它不依赖分数分布，只看"回答是否真的挂了来源"，最直接地对应"答案溯源"。

### 4.4 阈值标定流程（用 R11 的评测能力）

1. 用 R11 评测集跑 `dense`，导出每条问题的 top1 分数；
2. 把有答案 / 无答案两组分数画分布，找"误拒率 ≤ 5% 时泄漏率最低"的点；
3. 同一阈值不要用到 hybrid / rerank；
4. 上线前用 15 条无答案问题回归，拒答率目标 ≥ 90%，同时有答案问题的误拒率 ≤ 5%。

### 4.5 验收

| 用例 | 期望 |
| --- | --- |
| 有答案 + 带引用 | 正常回答 |
| 有答案但模型没标引用 | L3 替换为拒答，日志记录 `citation_guard=reject` |
| 模型标 `[9]`（不存在） | L3 替换为拒答 |
| 无答案问题 | 拒答 + 引导人工 |
| 订单类问题（含订单号） | 放行（命中 `_GATE_BYPASS_RE`），走 `query_order`，不查知识库 |
| 无答案 + L1 开启（top-1=0.21） | 不调用模型，直接拒答；日志 `[R12 pre_gate] reject=low_score` |

### 4.6 踩坑

- 寒暄（"你好"）没有引用但 citations 为空 → 放行；一旦当天检索过资料（citations 非空），寒暄也可能被 L3 误杀 → 需要把 L3 作用范围限定为"调用了 search_kb 的轮次"。
- L1 开启后出现"该答没答" → 先看 `[R12 pre_gate]` 日志里的 `score`：若在 0.45~0.55 重叠区，说明阈值定得太高；若是订单/工单被拦，说明 `_GATE_BYPASS_RE` 漏词。两者都按 4.7.9 处理。
- 流式先吐后撤回 → 前端需要展示"已更正"提示，否则用户困惑。
- 拒答话术与结尾固定话术冲突 → 拒答时不要再追加"客服中心 | 工作时间"。

### 4.7 L1 前置闸门（可选，默认关闭）

> 一句话：在 Agent 调用之前先做一次 dense 检索，top-1 分数太低就直接拒答，**这一轮不调用模型**。
> 默认关闭（`ENABLE_PRE_RETRIEVAL_GATE=false`）：它买的是"省 token、省一次模型调用、少一个幻觉入口"，代价是"误拒"。

#### 4.7.1 它在链路里的位置

```text
用户问题
  │
  ├─ L1 前置闸门（本节）        ← 只做一次 dense top-1；低于阈值 → 直接拒答，结束
  │      └─ 放行
  ├─ Agent 决定是否调用 search_kb
  │      └─ search_kb 内部：hybrid → rerank → 分数阈值过滤（L2）→ 返回 [n] 编号
  ├─ LLM 生成
  └─ L3 引用校验（5.3）          ← 最后一个硬闸门
```

**L1 和 L2 不是一回事，别混**：

| 对比项 | L1 前置闸门 | L2 检索阈值过滤 |
|---|---|---|
| 时机 | 调用模型**之前** | `search_kb` 内部 |
| 动作 | 整题拒答，**不调用模型** | 剔除低分 chunk，仍然调用模型 |
| 省下的成本 | token + 一次完整模型调用 | 只减少 prompt 噪声 |
| 误拒后果 | 用户直接看到拒答，没有兜底 | 模型还能用剩余资料/常识回答 |
| 开关 | `ENABLE_PRE_RETRIEVAL_GATE` | `ENABLE_RETRIEVAL_SCORE_THRESHOLD` |

这也是为什么 L1 只能做"明显越界"的拦截：它的误拒没有补救机会，而 L2 的误拒至少还有模型兜底。

#### 4.7.2 拦什么、不拦什么

判定顺序是"先放行、再打分"：任一放行条件命中就立即结束，全部不命中才看分数（fail-open）：

| 输入 | dense top-1 | 结果 | 原因 |
|---|---|---|---|
| "退货运费谁承担" | 0.72 | 放行 | 知识库覆盖 |
| "今天天气怎么样" | 0.21 | 拒答 | 明确越界，省一次模型调用 |
| "我的订单到哪了" | 0.30 | 放行 | 命中订单类关键词，交给 `query_order` |
| "你好" / "谢谢" / "转人工" | 任意 | 放行 | 寒暄/转人工本来就不查知识库 |
| 知识库未就绪 / 检索异常 | 未知 | 放行 | fail-open，不能因为闸门故障阻断对话 |

**边界模糊的问题不归 L1 管**。比如"赠品能不能退货"这种知识库可能覆盖、也可能不覆盖的问题，top-1 常落在 0.45~0.55 的重叠区，应该交给 L2 + L3，而不是让 L1 赌一把。

#### 4.7.3 为什么默认关闭：三个代价

1. **延迟**：多一次 `embedding + ANN`，约 30~120ms（取决于 embedding 服务网络）。对首 token 时间本来就 1~2s 的链路，这是 5%~10% 的额外开销。
2. **误拒**：R11 已证明有答案/无答案的 dense 分数重叠（有答案最低 0.497，无答案中位数 0.547）。L1 一拒就是"这轮没有回答"，误拒代价比 L2 高。
3. **覆盖不全**：寒暄、订单、工单要靠规则放行，规则漏一条就误杀；多轮指代（"那这个呢"）目前没有规则可放行，只能靠关闭 L1 规避。规则永远补不完。

结论：**当前阶段 L3 是主力，L1 只作为"知识库覆盖范围明确 + 越界问题占比高"时的可选优化**。8 篇文档的小 KB 更适合先开 L1 做实验，而不是直接上生产。

#### 4.7.4 实现（[tools.py](file:///Users/changwenbiao/PycharmProjects/ai_customer_service/python_agent/tools.py#L105-L176)，日志分支略）

```python
# 订单/物流/工单/转人工这类问题本来就不查知识库，必须先放行
_GATE_BYPASS_RE = re.compile(
    r"订单|物流|快递|发货|运单|退款进度|工单|转人工|人工客服|投诉|售后进度|查件"
)
# 寒暄短路：必须整句就是寒暄，所以用 ^...$ 全句匹配；
# "退货怎么算"这类含内容词的问句不会被放行
_GREETING_RE = re.compile(
    r"^(?:你好|您好|在吗|在不在|在么|嗨|哈喽|hi|hello|谢谢|多谢|感谢|再见|拜拜|好的|ok|嗯)"
    r"[呀啊哦呢。！？!?~～\s]*$",
    re.IGNORECASE,
)


async def pre_retrieval_gate(user_message: str) -> str | None:
    """L1 前置闸门：返回 None = 放行；返回字符串 = 直接拒答（该字符串就是最终回复）。"""
    if not ENABLE_PRE_RETRIEVAL_GATE:
        return None

    text = (user_message or "").strip()
    if not text:
        return None
    if _GREETING_RE.match(text) or _GATE_BYPASS_RE.search(text):
        return None

    tid = _tenant_var.get() if _tenant_var is not None else ""
    store = _app.state.tenant_stores.get(tid) if _app is not None else None
    if store is None:                 # 知识库未就绪 → 放行
        return None

    try:
        pairs = await store.asimilarity_search_with_score(text, k=1, mode="dense")
    except TypeError:                 # 兼容不支持 mode 参数的旧 store
        try:
            pairs = await store.asimilarity_search_with_score(text, k=1)
        except Exception:
            return None               # 检索异常 → 放行
    except Exception:
        return None                   # 检索异常 → 放行

    if not pairs:                     # 空 KB：整库无覆盖，拒答
        return REJECT_REPLY
    if float(pairs[0][1]) < PRE_RETRIEVAL_GATE_THRESHOLD:
        return REJECT_REPLY
    return None
```

| 取舍 | 原因 |
|---|---|
| **只用 dense** | 只有 cosine 分数在 0~1 稳定可比；hybrid 的 RRF 分是排名倒数（rank1 恒 0.5），rerank 是对数似然（可负），三者不能共用阈值 |
| **fail-open** | 闸门的价值是"省钱"，不是"正确性"；检索异常/知识库未就绪时放行，绝不让闸门故障阻断对话 |
| **不写 citations / kb_hits** | 闸门检索不是用户可见的引用。写进 ContextVar 会让 L3 以为"本轮有资料"，把寒暄误杀成"有资料却没引用" |
| **寒暄用全句匹配** | 子串匹配会把"你好，退货运费谁承担"整句放行；`^...$` 全句匹配只放行"你好""谢谢"这种纯寒暄 |

#### 4.7.7 阈值怎么标定

不要凭感觉填 0.35。按 R11 的流程走：

1. 用 R11 评测集跑 `--mode retrieval` 的 dense 链路，导出每条 query 的 top-1 分数；
2. 分"有答案 / 无答案"两组画分布，做阈值扫描，得到每个阈值下的误拒率与泄漏率；
3. 选"**误拒率 ≤ 5% 时泄漏率最低**"的点；
4. 把这个值填进 `PRE_RETRIEVAL_GATE_THRESHOLD`，再用 100 条评测集离线回放一次。

几个容易踩的标定错误：

- **不要拿 RRF 分数标定**：hybrid 的 rank1 恒为 0.5，阈值扫描会失效（R11 2.6 已解释）。
- **不要拿 rerank 分数标定**：cross-encoder 是对数似然，可正可负，和 cosine 不是一个量纲。
- **0.35 是保守值**：R11 有答案最低分 0.497，所以 0.35 基本只拦"明显离群"问题，误拒几乎为零；想更激进可试 0.45~0.50，但误拒率会明显上升。
- **不要用同一阈值跑不同 embedding 模型**：换模型必须重新扫描。

### 5.1 [n] 编号：检索结果结构化 + 引用采集（原 Step 1）

#### 5.1.1 为什么不直接把 JSON 返回给模型

- 模型对 JSON 的字段遵循不稳定，容易漏字段、编字段；
- 编号文本（`[1] xxx`）最接近模型的自然引用习惯，prompt 约束成本最低；
- 但程序又需要结构化数据（doc_id、标题、分数）来落库和前端展示。
- 所以拆成两份：**给模型的是编号文本，给程序的是 ContextVar 里的结构化列表**。

#### 5.1.2 数据结构

```python
Citation = {
    "index":   int,     # 全局编号，正文 [n] 与之对应

    "title":   str,     # 文档标题
    "section": str,     # 标题路径（R11 实验 E 产出的 section）
    "snippet": str,     # 原文前 200 字，前端折叠展示
    "score":   float,   # 检索/重排分数，仅用于调试与阈值分析

```

#### 5.1.3 为什么用 ContextVar 而不是全局 list

`/agent/chat` 与 `/agent/chat/stream` 是并发的，工具函数内部拿不到"这次请求"的局部变量；全局 list 会串请求。
`contextvars.ContextVar` 在 asyncio 任务内有独立副本，天然按请求隔离，无需透传参数。

```python
# 单次请求内累积的引用；ContextVar 保证并发请求互不污染
_citations_var: ContextVar[list[dict]] = ContextVar("kb_citations", default=[])


def reset_citations() -> None:
    """每次 /agent/chat 或 /agent/chat/stream 入口调用一次"""
    _citations_var.set([])


def get_citations() -> list[dict]:
    return list(_citations_var.get())


def _append_citations(pairs: list[tuple]) -> list[int]:
    """把本次命中的 (Document, score) 追加进引用列表，返回它们在正文中的编号"""
    current = _citations_var.get()
    start = len(current)                      # 跨多次 search_kb 调用继续编号
    for i, (doc, score) in enumerate(pairs, start=1):
        meta = doc.metadata or {}
        current.append({
            "index": start + i,
            "doc_id": meta.get("doc_id", ""),
            "title": meta.get("title", ""),
            "section": meta.get("section", ""),
            "snippet": (doc.page_content or "")[:200],
            "score": round(float(score), 4),
        })
    _citations_var.set(current)
    return [c["index"] for c in current[start:]]
```

### 5.3 后置引用校验（L3，原 Step 5）

```python
import re
from tools import get_citations

REJECT_REPLY = "这个问题我暂时没有查到准确信息，建议转接人工客服进一步确认。"


def citation_guard(answer: str, citations: list[dict]) -> tuple[str, bool]:
    """返回 (最终回答, 是否被降级为拒答)"""
    if not answer:
        return REJECT_REPLY, True

    # 本次没有检索到任何资料：可能是寒暄、订单查询等非知识库问题，放行
    if not citations:
        return answer, False

    valid = {c["index"] for c in citations}
    used = {int(n) for n in re.findall(r"\[(\d+)\]", answer)}

    # 有资料但没有任何引用 → 视为无依据回答
    if not used:
        return REJECT_REPLY, True
    # 引用了不存在的编号 → 视为编造来源
    if not used.issubset(valid):
        return REJECT_REPLY, True
    return answer, False
```

- 简单：校验失败时追加一条系统提示"以上回答未通过溯源校验，请以人工客服确认为准"，并推送 `end` 的 `content` 为替换后的文本；
- 彻底：流式阶段先缓冲（不逐 token 推送），`end` 前校验，再一次性推送。**R12 建议先用第一种**，不破坏现有体验。

## 第六章 · 闸门三：事实对不对（原 Step 6）

### 6.1 为什么要单独做

金额、时效、比例是最容易被"参数记忆"污染，也最容易被用户当成承诺。即使整体有引用，句子里数字仍可能是模型自己算的。

### 6.2 规则

- 回答中出现 `天/日/小时/个工作日/元/%/折` 的数字，必须**同句或相邻位置**带 `[n]`；
- 订单相关数字必须来自 `query_order` 返回值，不允许从知识库推断；
- 无法溯源的数字 → 删除该句或整条降级为拒答。

### 6.3 代码（放在 `citation_guard` 之后）

```python
NUM_RE = re.compile(r"\d+(?:\.\d+)?\s*(?:天|日|小时|个工作日|元|%|折)")

def number_guard(answer: str, citations: list[dict]) -> tuple[str, bool]:
    if not citations:
        return answer, False
    ok = True
    for sent in re.split(r"[。！？\n]", answer):
        if NUM_RE.search(sent) and not re.search(r"\[\d+\]", sent):
            ok = False
            break
    if ok:
        return answer, False
    return REJECT_REPLY, True
```

> 规则很陡：一句话里出现两个事实、只有一个引用，也会被判失败。可放宽为"整段至少有一个引用"，但效果会打折；建议先严后松，用评测数据决定。

### 6.4 Prompt 侧配合

在 system prompt 的第 2 条后补充：

```
涉及金额、时效、比例的数字，引用编号必须紧跟在数字所在句子后面。
```

```js
function renderCitations(container, citations) {
  if (!citations || !citations.length) return;
  if (container.querySelector('.cite-box')) return;   // 防止重复插入

  const box = document.createElement('div');
  box.className = 'cite-box';

  const head = document.createElement('div');
  head.className = 'cite-head';
  head.textContent = `参考来源（${citations.length}）`;

  const list = document.createElement('div');
  list.className = 'cite-list';
  list.style.display = 'none';

  citations.forEach(c => {
    const item = document.createElement('div');
    item.className = 'cite-item';
    item.innerHTML =
      `<div class="cite-title">[${c.index}] ${esc(c.title || '未命名文档')}` +
      (c.section ? `<span class="cite-sec"> · ${esc(c.section)}</span>` : '') + `</div>` +
      `<div class="cite-snippet">${esc(c.snippet || '')}</div>`;
    list.appendChild(item);
  });

  head.onclick = () => {
    list.style.display = list.style.display === 'none' ? 'block' : 'none';
  };
  box.appendChild(head);
  box.appendChild(list);
  container.appendChild(box);
}
```

> `esc()` 在 pc.html 已有（`escapeHtml` 类工具函数），复用即可；**不要直接拼未转义的 snippet**，知识库文档可能含 `<`。

### 7.3 自一致性校验（加分，原 Step 7）

#### 7.3.1 适用条件

只对**高风险问题**启用：金额、时效、退换货政策、涉及承诺的结论。全量启用成本和延迟都不可接受。

#### 7.3.2 做法

同一问题用较高温度采样 3 次，取最终 AIMessage：

```python
async def self_consistency(agent, payload, n=3) -> tuple[str, bool]:
    outs = []
    for _ in range(n):
        result = await agent.ainvoke(payload)
        outs.append(_last_ai_content(result))
    # 归一化：去空白、去标点、去引用编号后再比较
    norm = [re.sub(r"[^\w\u4e00-\u9fa5]", "", o) for o in outs]
    if len(set(norm)) > 1:
        # 任一不一致 → 说明模型对该事实没有稳定把握
        return REJECT_REPLY, True
    return outs[0], False
```

#### 7.3.3 成本控制

- 只对 `number_guard` 命中的问题、或租户配置的高风险意图启用；
- 采样结果可缓存（同问题 + 同知识库版本）；
- 默认关闭，用配置开关 `ENABLE_SELF_CONSISTENCY=false`。

#### 7.3.4 结论怎么写进项目说明

"自一致性只作为离线抽检手段，不做线上主链路"——因为 3 次调用会把 P95 延迟和成本放大 3 倍，而 L3 引用校验已经能覆盖大部分幻觉。

## 附录 B：面试怎么讲（详细版）

> 讲法原则：**先讲为什么问题严重 → 再讲我是怎么拆解的 → 再报数字 → 主动承认坑与成本**。
> 幻觉治理的核心卖点是"我没有说'我把幻觉清零了'——我说'我把幻觉分成三层，每层有独立闸门，单靠 prompt 不行'"。

### B.1 30 秒电梯版（开场自我介绍）

> "我做过一个电商客服 RAG 的幻觉治理专项：先给检索到的每个 chunk 分配编号（grounding 锚点）、用 prompt 逼模型引用 `[n]`、生成完程序正则校验 `[n] ⊆ citations`——不合法就直接拒答。同时证明了单靠相似度阈值拒答是不可能的（R11 分布重叠 60% 泄漏），所以拒答必须靠程序侧硬闸门。"

### B.2 90 秒 STAR 版（面试主叙述）

**S 背景**：电商客服，AI 客服答"运费平台承担"但实际买家承担，用户投诉公司赔；这类答得流畅但事实错误的问题，比答不上来破坏大 10 倍。

**T 任务**：消除可量化事实错误 + 让其余幻觉可追溯可拒答，同时不能让有答案问题准确率显著下降。

**A 行动**（按落地顺序，体现方法论）：

1. **拆幻觉**：RAG 幻觉分三类——检索未召回（R11 解决）、生成未 grounded、引用幻觉。后者都可以用 citation 机制统一处理。
2. **造 grounding 锚点**：`search_kb` 返回 `[n]` 编号文本，程序把编号 → chunk 映射存 ContextVar。
3. **Prompt 强制引用**："每个结论后标 `[n]`；资料不足说不知道"——但这只是行为约束，不是保证。
4. **后置校验硬闸门**：生成完正则 `[n] ⊆ citations`，非法直接替换成固定拒答话术（不能让模型生成拒答，否则又会幻觉）。
5. **Go 透传 + 前端展示**：citations 随 SSE end 下发、`messages.metadata` 持久化、前端渲染折叠"参考来源"。
6. **数字校验加固**：金额/时效/比例必须和引用 chunk 里的数字一致。
7. **自一致性做离线**：3 次采样比对只做离线，线上主链路靠 Step 5 就够（3× 成本边际收益 5-10%）。

**R 结果**：无答案拒答率从 baseline 的 10% 提到 ≥90%；有答案引用覆盖率 100%；数字事实幻觉投诉降到零。同时证明了"单靠阈值不行"这个结论，推动了后续意图闸门方案。

### B.5 追问树（5 大类 20+ 问题）

#### A. 幻觉与 grounding

| 追问 | 回答 | 加分点 / 坑 |
|---|---|---|
| 怎么防幻觉？ | 不是只改 prompt。三层：检索编号化 → prompt 强制引用 → 后置正则校验拒答；阈值只做辅助；数字事实走工具 | 核心观点"拒答是风控不是体验" |
| 幻觉分几类？ | 三类：检索未召回（R11）、生成未 grounded、引用幻觉（Step 5 解决后两类） | 能拆解说明不是笼统说"大模型天生会瞎编" |
| 生成未 grounded 和引用幻觉什么区别？ | 前者：正确 chunk 在 prompt 里但模型没用上或理解错（答"平台承担"但资料写"买家承担"）；后者：编不存在的 `[9]`（更极端） | 两者都能被 Step 5 捕获，但前者的 claim-level 匹配还可以加 LLM-as-judge |
| grounding 为什么难？ | LLM 训练目标是"预测下一个最可能 token"，不是"严格遵循资料"；prompt 只是上下文的一部分，会被"稀释" | 从训练目标层面解释，不是"模型不听话" |
| CiteGuard-RAG 消融实验说明了什么？ | 检索 99.1% 准确 → 去掉后置验证模块，grounded-accuracy 从 98.3% 跌到 ~70%；**检索好 + prompt 约束 ≠ grounded 生成** | 这是"为什么必须有 Step 5"的铁证 |

#### B. Citation 机制

| 追问 | 回答 | 加分点 / 坑 |
|---|---|---|
| citation 怎么保证不是编的？ | 编号由 `search_kb` 返回时程序分配（ContextVar 并发安全），模型不能凭空造 `[9]`；后置正则 `[n] ⊆ citations` 越界即拒答 | 关键是"编号是程序的，不是模型的" |
| citation 为什么是 grounding 的关键？ | 把 grounding 从"模型的软承诺"（"我从资料里找答案"）变成"编号的硬契约"（"我引用了资料编号 1"）；程序能机械校验 | 数学本质 |
| 正则校验为什么够？会不会太粗？ | 正则校验是**必要不充分**条件：保证引用的编号都是真实的；不保证编号对应的 chunk 真支持这个 claim。充分条件可以加 LLM-as-judge，但正则是零成本 100% 可靠的硬闸门，必须先做 | 承认局限，但说清为什么够 |
| ContextVar 为什么用不用全局 list？ | 并发请求下全局 list 会互相污染；ContextVar 是线程/协程隔离的本地变量，async 安全 | 提到 LangGraph / fastapi 的并发模型 |
| Prompt 被 DB 覆盖怎么办？ | config.py 的默认值只 seed 空 DB；已有 active prompt 的租户需要手动 UPDATE | 真实运维坑 |

#### C. 拒答策略

| 追问 | 回答 | 加分点 / 坑 |
|---|---|---|
| 三类拒答策略各自的代价？ | L1 前置意图闸门：低，但分类器有误判；L2 阈值兜底：零，但分布重叠（R11 已证）；L3 后置引用校验：低（正则），但 claim 匹配不充分 | 成本/风险/收益三维对比 |
| 为什么阈值不能单独拒答？ | R11 实测分布重叠：无答案最高 0.650、有答案最低 0.497；任何阈值都只能在误拒 ↔ 泄漏间做交换 | 必须带数字，不要说"我觉得阈值不行" |
| 拒答话术为什么是固定模板？ | 不能让模型生成拒答话术，否则又会幻觉（说"退款最多 7 天"但资料里没有）；固定模板里连电话号码、引导语都写死 | 反常识但真实的决策 |
| 自一致性为什么不进线上主链路？ | 3× 成本 + 延迟；L3 已经解决 80%+ 幻觉；边际收益 5-10%；适合做离线抽检评估风险 | 说清 ROI 思路 |
| EverydayGPT 的 Confidence-Gated Routing？ | 把拒答建模成三选一路由 `π(q, D) → {RAG, GPT, REFUSE}`，核心是"拒答也是生成策略，不是异常处理" | 体现知道学术界进展 |

#### D. Prompt vs 程序 Guard

| 追问 | 回答 | 加分点 / 坑 |
|---|---|---|
| Prompt 和 guard 怎么分工？ | Prompt 是**行为约束**：让模型"尽量"做对；Guard 是**程序侧硬闸门**：不合法直接拒答。prompt 永远会漏，guard 100% 可靠 | 两层定位清晰 |
| Guard 怎么选？ | 先上**零成本正则**（`[n] ⊆ citations`、数字格式匹配）；不够再考虑 LLM-as-judge（claim-level 校验）；cost/benefit 排序 | 体现工程决策能力 |
| LLM-as-judge 能替代正则吗？ | 不能。LLM-as-judge 有成本（每条 claim ~100 tokens）、有波动、有 prompt sensitivity；正则是零成本 100% 可靠的底线 | 承认 judge 是增量、不是替代品 |
| Guard 和 content_guard 签名校验打架怎么办？ | 两条 guard 串行执行、统一返回"拒答话术"而不是抛异常；最后一条 guard 失败 → 直接替换 | 说清职责边界 |

#### E. 工程落地

| 追问 | 回答 | 加分点 / 坑 |
|---|---|---|
| 流式下怎么处理校验？ | 两种方案：(a) 完整拼完再推（~500ms 延迟，但不会先露错内容）；(b) 先推正文、end 时校验、失败推 `content_type=notice` 追加更正。我们选 (b) | 两种都能说清 trade-off |
| 拒答率和误拒率怎么平衡？ | 看分布重叠区间（R11 的 0.497~0.650）；L2 阈值设区间下限兜极端低分；L3 严格正则保证有答案不被误拒；同时监控两条曲线 | 不能只看一个指标 |
| 怎么上线 / 回滚？ | 步骤按 1+2 → 5 → 3+4 → 6 顺序，每步都能独立上线；Step 5 改完就能压幻觉、立刻见效（不需要 Go / 前端改）；回滚：重启还原 agent、revert prompt | 可灰度 |
| 线上监控什么指标？ | 拒答率 / 误拒率 / 引用覆盖率 / Faithfulness（线下定期评估）/ 数字事实投诉量 | 和业务对齐 |
| 为什么不能用 L1 意图分类器？ | 当前 KB 只有 8 篇文档、覆盖范围明确，15 条无答案题分桶清晰；等 KB 扩到 100+ 篇、有跨域边界时再加 L1 | 体现"当前阶段够用就好" |

#### F. 挑战型追问

| 追问 | 回答 |
|---|---|
| "你把幻觉清零了？" | 没有。我消灭的是**可量化事实错误**（投诉的 60%+），让其余幻觉**可追溯**（用户能点开引用看原文）。RAG 不能消所有幻觉，但能让幻觉可审计可定位。 |
| "引用校验会不会让模型变懒？" | 会！当模型引用随便标 `[1]`、而 chunk 又真的包含 claim 时，正则校验会放过去。所以需要定期用 LLM-as-judge 做离线抽检（第八章给了工具），或者在前端让用户点引用反馈"引用是否正确"。 |
| "如果检索没召回正确段落，但模型靠记忆答对了，还带了引用？" | 这种场景 Step 5 正则放过去（因为引用编号合法），但 claim-level 校验（L1 judge）会发现"claim 与 chunk 内容不匹配"。这就是为什么 L3 是必要不充分，还需要定期 LLM-as-judge。 |
| "CiteGuard-RAG 98.3% grounded-accuracy 是受控环境，你怎么保证线上？" | 线上有三个降级信号：(a) 引用覆盖率下降 → prompt 变弱了 / 模型变了；(b) 拒答率突升 → 校验正则太严 / 误判；(c) 投诉里数字幻觉 → 数字校验没覆盖到这个类别。每两周用 R11 评测集跑一遍回归。 |
| "你最大的贡献是什么？" | 把"防幻觉"从"改 prompt"变成**可分解、可验证、可量化**的工程问题。三层防线每层有独立机制和验收标准，拒答率/误拒率/引用覆盖率三个指标同时看。 |

### B.6 常见翻车说法与纠正

| 不要说 | 为什么错 | 应该说 |
|---|---|---|
| "我把幻觉清零了" | 不存在的承诺 | "消灭了可量化事实错误，其余幻觉可追溯可拒答" |
| "改 prompt 就能防幻觉" | prompt 不是硬闸门 | "prompt 是行为约束，还需要后置校验兜底" |
| "阈值调到 0.65 就能拒答" | 分布重叠，不存在两全 | "阈值只能兜极端低分，主力拒答靠引用校验" |
| "citation 是给用户看的" | 反过来了——先给程序校验，用户展示是附加 | "citation 先给程序做校验（Step 5），Go 透传展示是第二步" |
| "拒答率 ≥90% 就完了" | 必须同时看误拒率 | "拒答率 ≥90% 且误拒率 ≤5%，两者同时看" |
| "自一致性一定要做" | 3× 成本，边际收益低 | "自一致性做离线抽检，线上靠 Step 5+6 就够" |

### B.7 简历 / 项目 bullet 模板

- 搭建 RAG 幻觉治理三层防线：检索侧 `[n]` 编号 grounding 锚点 → prompt 强制引用 → 后置正则 `[n] ⊆ citations` 校验拒答，无答案拒答率从 10% 提升至 ≥90%。
- 实现 Go 侧 citations 透传 / 落库 + 前端参考来源可折叠展示，形成全链路溯源闭环。
- 通过阈值扫描量化证明"单靠相似度无法可靠拒答"（最优阈值仍有 60% 泄漏），推动三层拒答（abstention）策略选择。
- 设计数字类事实校验（金额/时效/比例），将高频高风险幻觉投诉（占比 60%+）降为零。

### B.8 一句话收尾

> "这个需求让我最满意的不是幻觉率降了多少，而是**之后任何 prompt 改动 / 模型切换 / 检索策略变化，都不会悄无声息地把幻觉带回来**——拒答率、误拒率、引用覆盖率三个指标会第一时间报警。"
