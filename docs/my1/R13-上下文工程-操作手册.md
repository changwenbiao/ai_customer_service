### 0.3 术语与口径

- **上下文窗口**：模型单次请求允许的最大输入 token（不是输出 `max_tokens`）。
- **预算**：`window - 输出上限 - 安全余量`。本项目的输出上限是 `max_tokens=1024`，因此预算要再减 1024。
- **软阈值**：触发摘要压缩的阈值，建议 `window * 0.55 ~ 0.65`。
- **硬阈值**：超过就必须裁剪，建议 `window - 1024 - 512`。
- **上下文占比**：`估算 prompt tokens / window`，每轮记录，曲线应趋于平台而不是单调上升。
- **槽位（slot）**：跨轮必须保持的关键事实，例如订单号、手机号后四位、工单号、金额、商品名。

### 0.4 为什么现在的架构一定会膨胀

当前每条用户消息只带一句 `HumanMessage` 进 Agent，但 checkpointer 会把「用户消息 + AI 回复 + 每次工具调用 + 每次工具结果」全部累积在 state 里。30 轮里只要有 10 次知识库检索（每次 3 个 chunk、每 chunk 约 250 字），仅历史工具结果就有约 7.5k 字符；再加历史对话，单轮 prompt 很容易到 6k~15k token。

`token_usage` 记录的是**真实 API 输入 token**，所以 Step 1 完全不需要额外埋点就能看到这条曲线。

## 第一章 Step 1：先量出来（基线）

### 1.1 为什么要先量

没有基线就无法判断：
- 30 轮后到底涨到多少；
- 是历史对话在涨，还是工具结果在涨；
- 摘要把 token 压下来后，首 token 延迟是否反而变差（摘要本身要调一次模型）。

### 1.2 用现有 `token_usage` 做基线

`token_usage` 每轮都会写入真实 `input_tokens / output_tokens`。直接查：

```sql
-- 把 thread_id 换成你的测试线程
SELECT id,
       created_at,
       input_tokens,
       output_tokens,
       round(input_tokens::numeric / 8192, 2) AS ratio_to_8k
FROM token_usage
WHERE thread_id = 't_demo:ctx_20261103'
ORDER BY id;
```

如果这张表里没有 `thread_id` 字段或为空，先确认 [db_ops.py](file:///Users/changwenbiao/PycharmProjects/ai_customer_service/python_agent/db_ops.py#L127-L157) 的 `INSERT` 是否带上了 thread_id（当前实现已带）。

### 1.3 30 轮压测脚本（已落地）

30 轮 SSE 压测脚本**已经落地**在 [R13/context_stress.py](file:///Users/changwenbiao/PycharmProjects/ai_customer_service/python_agent/R13/context_stress.py)。

### 1.4 每轮上下文审计日志

基线阶段先只做「观测」，不改任何行为。在 Step 3 的中间件里加一行结构化日志即可：

```
context_budget thread=t_demo:ctx_20261103 msgs=28 est=5120 ratio=0.62 actions=tool_stub:3,summary:1 summary_len=120 slots=2
```

字段含义：

| 字段 | 说明 | 用途 |
|---|---|---|
| `msgs` | 本轮进入模型的 state 消息数 | 看历史是否在涨 |
| `est` | 估算 prompt token（system + state 消息；工具 schema 约 300~500 未计入，校准时统一吸收） | 与 `token_usage.input_tokens` 对照校准 |
| `ratio` | `est / window` | 判断是否越预算 |
| `actions` | 本轮裁剪动作及次数 | 定位是哪一层在起作用 |
| `summary_len` | 注入的历史摘要长度 | 摘要太长本身也是成本 |
| `slots` | 注入的槽位数量 | 验证关键实体是否还在 |

#### 发现的三个问题及修复

##### 问题 1：后半程 429 雪崩（根因 + 现象 + 修复）

**现象链**：

| 阶段 | 表现 | 说明 |
|---|---|---|
| 1-20 轮 | 基本 OK，平均 TTFT 3.2s，p95 10.7s | 基线数据可用，ttft 偏长的几轮都是输入量大的轮次（第 3 轮埋订单号、第 7 轮修改地址等） |
| 21 轮 | ttft=1.885s 但 total=32.5s、answer_len=1 | 请求进了 Agent，拿到模型返回但只有 1 字符，说明模型在被限流前输出了一小段就停了 |
| 22 轮 | ttft=0、total=30s | Agent 等了 30s 没拿到模型响应（SDK 在内部重试？或者 Agent 有自己的超时） |
| 23 轮起 | ttft=0、total < 1s | SDK 直接抛 429，根本没进模型 |

**根因**：glm-4.5-flash 按**时间窗口内累积 token 数**限流（不是 QPS）。前 20 轮累积输入 ≈ 20 × 2000 = 40K+ tokens，一下子把供应商的限流窗口填满了。而且 checkpointer 让每轮的 prompt token 越来越多，到第 20 轮时单轮输入已经是第 1 轮的 2~3 倍——**上下文膨胀本身就是限流放大器**。

**修复**：脚本默认轮间等待从硬编码 0.3s 抽成 `--interval` 参数，默认改为 1.5s（[context_stress.py L290-291](file:///Users/changwenbiao/PycharmProjects/ai_customer_service/python_agent/R13/context_stress.py#L290-L291)）。限流严格的模型（如 glm-4.5-flash）建议 `--interval 3~5`。

**额外结论（给后续 Step 参考）**：R13 Step 3 的分层裁剪不仅是为了压成本，也是在**主动降低单轮 input_token，从源头降低触发限流的概率**。如果有条件，Agent 端应在检测到连续 429 时做带指数退避的重试，而不是直接把 error 透传给前端——这可以挂在 SummarizationMiddleware 之外再叠一层轻量的 429 handler。

##### 问题 2：`--show-baseline` 连不上数据库

**现象**：压测跑完，最后一行报 `⚠️ 未找到 DATABASE_URL / PSYCOPG_DSN`。

**根因**：脚本只查 `DATABASE_URL` 和 `PSYCOPG_DSN`，但 Agent 真实用的是 `POSTGRES_DSN`（[config.py L17](file:///Users/changwenbiao/PycharmProjects/ai_customer_service/python_agent/config.py#L17)），且 dotenv 加载顺序也不对——Agent 是先读**项目根目录** `.env` 再读 `python_agent/.env` 和 `.env.local` override。脚本之前只读了后两个，根目录 `.env` 里的 `POSTGRES_DSN` 根本没被加载。

**修复**：脚本里的 dotenv 加载完全对齐 [main.py](file:///Users/changwenbiao/PycharmProjects/ai_customer_service/python_agent/main.py) 顺序（[context_stress.py L227-230](file:///Users/changwenbiao/PycharmProjects/ai_customer_service/python_agent/R13/context_stress.py#L227-L230)），DSN 查找改成 `POSTGRES_DSN → PSYCOPG_DSN → DATABASE_URL`（[L235-238](file:///Users/changwenbiao/PycharmProjects/ai_customer_service/python_agent/R13/context_stress.py#L235-L238)）。修复后在 shell 里验证：


##### 问题 3：第 25 轮事实回忆 FAIL 无意义

脚本在第 25 轮自动检查回答里是否出现 `ORD-2024-001`。但如果第 25 轮请求本身因为 429 失败，就不是模型记不住事实，而是请求根本没进模型。脚本已加判断——请求有 error 时，事实回忆报错信息而非误报 FAIL（[context_stress.py L154-157](file:///Users/changwenbiao/PycharmProjects/ai_customer_service/python_agent/R13/context_stress.py#L154-L157) + [L198-199](file:///Users/changwenbiao/PycharmProjects/ai_customer_service/python_agent/R13/context_stress.py#L198-L199)）。

#### 重跑建议（30 轮完整基线）

glm-4.5-flash 限流窗口紧，推荐两种策略。

**策略 A（推荐，最稳）**：直接把 interval 拉到 3~5 秒，30 轮约需 4~6 分钟。

```bash

/opt/miniconda3/envs/cs-agent-local/bin/python R13/context_stress.py \
```

```bash
  --thread-id <第一组输出里的 thread_id>
```

两组跑完后，去 DB 查同一个 thread_id 的 token_usage，应该能看到完整 30 轮曲线。

| 30 | 预期 > 8192 | > 1.0 | — | 峰值 |
| 峰值 | 见曲线 | 应超过窗口 | — | 证明 Step 1 有效 |

如果第 25 轮事实回忆通过，说明模型本身能记住，R13 槽位是加分项；如果 FAIL，必须优先落 Step 5 槽位。

## 第二章 Step 2：建立 Token 预算模型

### 2.1 预算公式

```
可用输入预算 = CONTEXT_WINDOW_TOKENS - OUTPUT_MAX_TOKENS(1024) - SAFETY(512)
软阈值       = CONTEXT_WINDOW_TOKENS * CONTEXT_SOFT_RATIO(0.60) - 静态开销
硬阈值       = 可用输入预算
```

**不要**把 `max_tokens`（输出上限）当成上下文窗口。`max_tokens=1024` 只限制输出，不影响输入上限，但会占用窗口，所以要从预算里扣掉。

### 2.2 Token 计数函数

模型供应商（DeepSeek / Qwen / 豆包）没有公开的本地 tokenizer，因此采用两条路并用：
1. 本地 `tiktoken cl100k_base` 作为估算器（对中英文混合比「字符数/4」准得多）；
2. 用 `token_usage.input_tokens` 反算校准系数，把估算误差压到 ±10% 以内。

新建 `python_agent/context_budget.py`，先放计数部分：

```python
- 裁剪：工具结果截断 → 摘要压缩 → 硬裁剪兜底
- 记忆：Go session_summaries 摘要 + Redis 关键实体槽位

import logging
import re
from contextvars import ContextVar

# ---------------------------------------------------------------------------
# 1. Token 计数
# ---------------------------------------------------------------------------
try:
    import tiktoken

    _ENC = tiktoken.get_encoding("cl100k_base")

    def _count_text(text: str) -> int:
        return len(_ENC.encode(text, disallowed_special=()))

except Exception:  # pragma: no cover - 容器未装 tiktoken 时退化
    _CJK_RE = re.compile(r"[\u4e00-\u9fff\u3040-\u30ff\uac00-\ud7af]")

    def _count_text(text: str) -> int:
        cjk = len(_CJK_RE.findall(text))
        other = len(text) - cjk
        return int(cjk * 0.75 + other / 4) + 1


def count_context_tokens(messages: list[Any]) -> int:
    """估算一组消息的 prompt token（给 SummarizationMiddleware 用）。"""
    total = 0
    for m in messages:
        total += 3  # 角色/分隔符开销
        content = m.content
        if isinstance(content, str):
            total += _count_text(content)
        else:
            total += _count_text(str(content))
        for tc in getattr(m, "tool_calls", None) or []:
            total += _count_text(json.dumps(tc, ensure_ascii=False))
        if isinstance(m, ToolMessage):
            total += _count_text(m.tool_call_id or "")
    return total
```

### 2.4 怎么确定 `CONTEXT_WINDOW_TOKENS`

1. 查当前用的模型：
```sql
SELECT model, count(*) AS rounds, max(input_tokens) AS max_input
FROM token_usage
WHERE created_at > now() - interval '7 day'
GROUP BY model;
```
2. 去模型供应商文档确认「最大输入上下文」；
3. 取 `min(供应商上限, 你的成本上限)` 填进环境变量；
4. 不要把 `CONTEXT_WINDOW_TOKENS` 填得比真实上限大，否则裁剪形同虚设，最终还是 API 报错（R14 兜底）。

### 2.5 校准估算器

跑 10 轮后，把日志里的 `est` 与 `token_usage.input_tokens` 对齐：

```
误差率 = (est - input_tokens) / input_tokens
```

- 误差在 ±15% 内：可以直接用；
- 系统性偏低（`est` 明显小）：把 `_count_text` 的 CJK 系数从 0.75 调到 0.9；
- 系统性偏高：降到 0.6，或在 `CONTEXT_STATIC_OVERHEAD_TOKENS` 上修正。

## 第三章 Step 3：分层裁剪（核心）

### 3.1 裁剪优先级

从「最不伤信息」到「最伤信息」：

| 顺序 | 动作 | 触发条件 | 保留什么 |
|---|---|---|---|
| 1 | 旧工具结果压成一行 | 超过最近 `TOOL_RESULT_KEEP_LAST` 条 | 工具名 + 前 200 字 |
| 2 | 最近工具结果头尾截断 | 单条 > `TOOL_RESULT_MAX_CHARS` | 头 60% + 尾 40% |
| 3 | 摘要压缩 | `messages > 24` 或 `tokens > 0.55*window` | 结构化摘要 + 最近 6 条 |
| 4 | 检索条数降级（可选） | 软阈值以上 | `k` 从 3 降到 2 |
| 5 | 硬裁剪兜底 | 超过硬阈值 | 最近消息，必要时截断单条 |

**顺序不能反**：先摘要再硬裁剪会导致摘要刚生成又被裁掉；先硬裁剪再摘要会丢失可摘要的信息。

#### 额外价值：裁剪同时降低限流风险

1.6 节首次压测的教训——glm-4.5-flash 按时间窗口内累积 token 数限流，而上下文膨胀让**每轮 prompt token 逐轮变多**，相当于主动往限流窗口里塞数据。裁剪不仅压成本，还直接降低触发 429 的概率：

- 原来：第 20 轮 input ≈ 第 1 轮的 2~3 倍，单轮就能吃掉窗口的大部分配额；
- R13 后：每轮 input 趋于稳定（摘要后保持在预算内），不会出现「后面几轮因为累积爆了」的情况。

如果 Step 1 的 30 轮压测在第 20 轮后集中 429，Step 3 落完后用同样参数重跑一遍，429 轮数应降到 5 轮以内甚至零。

> 注意：这不是 429 的完整解决方案——连续 3 轮密集请求即使 prompt token 很小也可能触发限流。完整方案需要在 Agent 最外层再叠一层带指数退避的 429 重试（检测到 SDK 抛 429 时 sleep + retry），那是独立于 R13 的增强项；R13 裁剪只解决「上下文膨胀放大了限流窗口消耗」这个特定问题。

### 3.2 工具结果治理中间件

工具结果（尤其是 `search_kb` 的历史片段）是最大膨胀源。策略：
- 最近 4 条工具结果：超过 800 字符做「头 60% + 尾 40%」截断；
- 更早的工具结果：只保留前 200 字符，并标记「已归档，结论见摘要」；
- 用 `ToolMessage` 同 id 替换，保持 `tool_call_id` 配对，避免破坏 AI/Tool 消息结构。

在 `context_budget.py` 继续追加：

```python
# ---------------------------------------------------------------------------
# 2. 工具结果治理
# ---------------------------------------------------------------------------
def _clip(text: str, limit: int) -> str:
    if len(text) <= limit:
        return text
    head = int(limit * 0.6)
    tail = limit - head
    return f"{text[:head]}\n...[中间内容已截断]...\n{text[-tail:]}"


def _content_to_text(content: Any) -> str:
    if isinstance(content, str):
        return content
    return json.dumps(content, ensure_ascii=False)


@before_model
def tool_result_guard(state, runtime):
    """① 旧工具结果压成一行；② 最近工具结果超长头尾截断。

    只替换 ToolMessage，不删除消息，保证 AI tool_call / ToolMessage 配对完整。
    """
    if not CONTEXT_BUDGET_ENABLED:
        return None
    msgs = state.get("messages") or []
    tool_msgs = [(i, m) for i, m in enumerate(msgs) if isinstance(m, ToolMessage)]
    if not tool_msgs:
        return None

    updates: list[ToolMessage] = []
    total_tools = len(tool_msgs)
    for order, (idx, m) in enumerate(tool_msgs):
        text = _content_to_text(m.content)
        is_recent = order >= total_tools - TOOL_RESULT_KEEP_LAST
        limit = TOOL_RESULT_MAX_CHARS if is_recent else TOOL_RESULT_STALE_CHARS
        if len(text) <= limit:
            continue
        clipped = _clip(text, limit)
        if not is_recent:
            tool_name = getattr(m, "name", None) or "unknown"
            clipped = (
                f"[较早工具结果已归档 | tool={tool_name} | 完整结论见会话摘要]\n" + clipped
            )
        # id 必须存在，否则无法原位替换（add_messages 按 id 覆盖）
        if m.id is None:
            continue
        updates.append(
            ToolMessage(
                content=clipped,
                tool_call_id=m.tool_call_id,
                id=m.id,
                name=getattr(m, "name", None),
            )
        )

    if not updates:
        return None
    _audit("tool_clip", n=len(updates))
    return {"messages": updates}
```

```python
# ---------------------------------------------------------------------------
# 4. 摘要压缩（带失败降级）
# ---------------------------------------------------------------------------
CONTEXT_SUMMARY_PROMPT = """你是一个电商客服会话的上下文压缩器。请把 <messages> 里的对话压缩成一份中文摘要。

必须遵守：
1. 只压缩，不编造。原文没有的信息不要补。
2. 必须原样保留：订单号、工单号、商品名、金额、时间承诺（如“48 小时内发货”）、已经给出的结论、用户明确提出的诉求、是否已转人工。
3. 用户身份线索（手机号后四位、会员等级）要保留。
4. 删除寒暄、重复追问、工具调用的原始大段文本。
5. 输出不超过 150 字，用「- 」开头的短句列表。

<messages>
{messages}
</messages>

摘要："""


def hard_trim(messages: list[Any], limit: int | None = None) -> dict:
    """硬裁剪兜底：保留最近的消息，尽量从 human 开始，允许截断最后一条。"""
    limit = limit or CONTEXT_HARD_LIMIT_TOKENS
    trimmed = trim_messages(
        messages,
        max_tokens=max(256, limit - CONTEXT_STATIC_OVERHEAD_TOKENS),
        token_counter=count_context_tokens,
        strategy="last",
        allow_partial=True,
        start_on="human",
        include_system=False,
    )
    _audit("hard_trim", kept=len(trimmed), dropped=len(messages) - len(trimmed))
    return {"messages": [RemoveMessage(id=REMOVE_ALL_MESSAGES), *trimmed]}


class SafeSummarizationMiddleware(SummarizationMiddleware):
    """摘要失败（限流/超时/模型报错）时降级为硬裁剪，保证本轮不失败。"""

    @staticmethod
    def _mark_if_summarized(result) -> None:
        if not result:
            return
        for m in result.get("messages") or []:
            if getattr(m, "additional_kwargs", {}).get("lc_source") == "summarization":
                _audit("summary")
                return

    def before_model(self, state, runtime):
        try:
            result = super().before_model(state, runtime)
            self._mark_if_summarized(result)
            return result
        except Exception as e:
            logger.warning("summarization failed, fallback hard_trim: %s", e)
            _audit("summary_failed")
            return hard_trim(state.get("messages") or [])

    async def abefore_model(self, state, runtime):
        try:
            result = await super().abefore_model(state, runtime)
            self._mark_if_summarized(result)
            return result
        except Exception as e:
            logger.warning("summarization failed, fallback hard_trim: %s", e)
            _audit("summary_failed")
            return hard_trim(state.get("messages") or [])


def build_summarization(model) -> SafeSummarizationMiddleware:
    return SafeSummarizationMiddleware(
        model=model,
        trigger=[
            ("messages", CONTEXT_SUMMARY_TRIGGER_MESSAGES),
            ("tokens", CONTEXT_SUMMARY_TRIGGER_TOKENS),
        ],
        keep=("messages", CONTEXT_SUMMARY_KEEP_MESSAGES),
        token_counter=count_context_tokens,
        summary_prompt=CONTEXT_SUMMARY_PROMPT,
        trim_tokens_to_summarize=CONTEXT_SUMMARY_INPUT_TOKENS,
    )
```

要点：

- `trigger` 是**或**关系：消息数到 24 或 state 消息估算 token 到「软阈值 - 固定开销」任一满足就摘要；
- `keep=6` 表示摘要后保留最近 6 条（约 3 轮），不要设成 0，否则模型会忘掉刚发生的事；
- 内置实现会自动保证裁剪点不切断 AI/Tool 配对，并在摘要前给消息补 id；
- 摘要本身是一次额外模型调用，触发那一轮 TTFT 会变高，这是正常成本，后面 Step 6 要量化。

### 3.4 硬裁剪兜底

硬阈值一定高于摘要触发阈值，所以走到这里时，摘要中间件已经至少尝试过一次；如果摘要失败（日志 `summary_failed`），才由硬裁剪接管。这正是需求里「极端情况先强制摘要一次，再继续」的落地方式：先摘要，失败才截断，绝不直接报错。

即使摘要成功，也可能因为「单条消息巨大」（例如一次工具返回异常长）仍然超硬阈值，所以再加一层：

### 4.3 修复「摘要只生成一次」

```go
func PendingSummaryCandidates(limit int) ([]PendingSummaryCandidate, error) {
	idle := config.GlobalConfig.SessionSummaryIdleMinutes
	if idle <= 0 {
		idle = 30
	}
	cutoff := time.Now().Add(-time.Duration(idle) * time.Minute)

	var threads []struct {
		ThreadID string
		TenantID string
	}
	// 关键变化：去掉 s.thread_id IS NULL，改成 HAVING 判断「消息比摘要更新」
	// 这样同一线程在新会话结束后会重新生成摘要，而不是永远停留在第一版
	if err := config.DB.Raw(`
		SELECT m.thread_id, m.tenant_id, MAX(m.created_at) AS last_active
		FROM messages m
		LEFT JOIN session_summaries s
		       ON s.thread_id = m.thread_id AND s.tenant_id = m.tenant_id
		WHERE m.created_at < ?
		GROUP BY m.thread_id, m.tenant_id, s.updated_at
		HAVING s.updated_at IS NULL OR MAX(m.created_at) > s.updated_at
		ORDER BY last_active DESC
		LIMIT ?`, cutoff, limit).Scan(&threads).Error; err != nil {
		return nil, err
	}
	// 下面的「取最近 40 条消息」逻辑保持不变
	...
}
```

注意 SQL 里的 `HAVING`：不能在 `WHERE` 里引用 `MAX(created_at)`，必须放到聚合之后的 `HAVING`。

```python
    try:
```

### 4.5 用 `dynamic_prompt` 注入 system

`create_agent` 的 `system_prompt` 是构建期静态的，不能按线程变化。LangChain 1.3 提供了 `@dynamic_prompt`，在每次模型调用前动态生成 system message，正好用来拼「原 Prompt + 历史背景 + 已知事实」。

在 `context_budget.py` 追加：

```python
@dynamic_prompt
def context_prompt(request):
    base = request.system_message.text if request.system_message else ""
    parts = [base.rstrip()]

    summary = _SUMMARY.get()
    if summary:
        parts.append(
            "## 历史背景（来自更早会话的自动摘要）\n"
            "以下内容只用于理解上下文，不是本轮知识库检索结果；涉及政策/事实时仍要检索并引用资料。\n"
            f"{summary}"
        )

    slots = _SLOTS.get()
    if slots:
        lines = []
        for k, vals in slots.items():
            if not vals:
                continue
            label = SLOT_LABELS.get(k, k)
            lines.append(f"- {label}：{'、'.join(vals)}")
        if lines:
            parts.append(
                "## 已知关键事实（来自本会话更早轮次）\n"
                "回答时直接使用这些信息，不要重复询问用户；若用户最新说法与这里冲突，以最新说法为准。\n"
                + "\n".join(lines)
            )

    final_prompt = "\n\n".join(p for p in parts if p)

    # 审计：最终 system + state 消息的估算值（每轮/每次模型调用都记）
    try:
        est = _count_text(final_prompt) + count_context_tokens(request.messages)
        _audit(
            "prompt_est",
            est=est,
            ratio=round(est / CONTEXT_WINDOW_TOKENS, 2),
            msgs=len(request.messages),
        )
    except Exception:
        pass
    return final_prompt
```

注意：
- `dynamic_prompt` 在**每次模型调用**（含工具循环的第二次调用）都会执行，函数里只能读内存/ContextVar，**不要做网络请求**；
- 摘要和槽位在请求入口就准备好，放进 ContextVar，保证同一请求内稳定；
- 这段是追加在 system 里，不改变 R12 的引用规则，也不替代检索；
- 内置 `SummarizationMiddleware` 生成的会话内摘要在 state 里是一条带 `lc_source=summarization` 的 `HumanMessage`（前面还有库自带的英文前缀），它不在 system 里；本节的「历史背景」是另一路跨会话摘要，两者不要混。

```python
        f"{a['action']}:{a.get('n', a.get('kept', 1))}"
```

## 第五章 Step 5：关键实体槽位（防摘要丢事实）

### 5.1 抽什么、不抽什么

只抽**强格式、可校验**的实体，宁可漏，不要错：

| 槽位 | 例子 | 抽取方式 |
|---|---|---|
| `order_id` | `ORD-2024-001` | 关键词「订单号/order id」+ 字母数字串 |
| `ticket_no` | `TK20261103001` | 关键词「工单号」 |
| `phone_tail` | 用户手机号后四位 `1234` | 关键词「手机/电话/联系方式」+ 11 位号码 |
| `amount` | `799 元` | 数字 + 元 |
| `product` | `VIP 年费会员` | 订单工具返回的 `订单 xxx：商品名 | ...` |

**不抽**：用户随口说的「大概」「昨天」「那个」等模糊指代；不抽模型自己生成的数字（只从用户消息与工具结果抽）。

### 5.2 Redis 存取

在 `context_budget.py` 追加：

```python
import re

SLOT_LABELS = {
    "order_id": "订单号",
    "ticket_no": "工单号",
    "phone_tail": "手机号后四位",
    "amount": "金额",
    "product": "商品",
}

_SLOT_RULES = {
    "order_id": re.compile(
        r"(?:订单号?|order\s*id)[^\w\-]{0,8}([A-Za-z0-9][A-Za-z0-9\-]{5,31})", re.I
    ),
    "ticket_no": re.compile(
        r"(?:工单号?)[^\w\-]{0,8}([A-Za-z0-9][A-Za-z0-9\-]{5,31})", re.I
    ),
    "phone_tail": re.compile(r"(?:手机|电话|联系方式)[^\d]{0,8}(\d{3})\d{4}(\d{4})"),
    "amount": re.compile(r"([0-9]+(?:\.[0-9]+)?)\s*元"),
    "product": re.compile(r"订单\s*[A-Za-z0-9\-]+[：:]\s*([^|｜\n]{2,30})"),
}

_MAX_SLOT_VALUES = 5


def _slot_key(thread_id: str) -> str:
    return f"cs:ctx:slots:{thread_id}"


def extract_slots(text: str) -> dict[str, list[str]]:
    found: dict[str, list[str]] = {}
    if not text:
        return found

    m = _SLOT_RULES["phone_tail"].search(text)
    if m:
        found.setdefault("phone_tail", []).append(m.group(2))

    for key in ("order_id", "ticket_no", "amount", "product"):
        for match in _SLOT_RULES[key].findall(text):
            value = match.strip()
            if value:
                found.setdefault(key, []).append(value)
    return found


async def load_slots(app, thread_id: str) -> dict[str, list[str]]:
    rc = getattr(app.state, "redis_client", None)
    if rc is None:
        return {}
    try:
        raw = await rc.get(_slot_key(thread_id))
        if raw is None:
            return {}
        text = raw.decode() if isinstance(raw, bytes) else str(raw)
        data = json.loads(text)
        return {k: [str(v) for v in vals][-_MAX_SLOT_VALUES:] for k, vals in data.items()}
    except Exception:
        return {}


async def merge_slots(app, thread_id: str, texts: list[str]) -> dict[str, list[str]]:
    """把新文本里的实体并入已有槽位；只保留最近 5 个值，写回 Redis。"""
    slots = await load_slots(app, thread_id)
    for text in texts:
        for key, vals in extract_slots(text).items():
            bucket = slots.setdefault(key, [])
            for v in vals:
                if v in bucket:
                    bucket.remove(v)
                bucket.append(v)
            slots[key] = bucket[-_MAX_SLOT_VALUES:]

    rc = getattr(app.state, "redis_client", None)
    if rc is not None and slots:
        try:
            await rc.set(
                _slot_key(thread_id),
                json.dumps(slots, ensure_ascii=False),
                ex=CONTEXT_SLOT_TTL_SECONDS,
            )
        except Exception as e:
            logger.warning("persist slots failed: %s", e)
    return slots
```

**为什么用 Redis 而不是加表**：
- 槽位是短生命周期（7 天）的会话工作记忆，和 checkpoint 回收周期一致；
- 不引入 DDL / 不修改 init.sql，部署成本最低；
- 若后续需要审计槽位，再加 `session_meta.slots JSONB` 也可以，接口不变。

### 5.4 注入顺序与冲突

system prompt 里三段顺序固定：

```
1) 原 system prompt（DB 驱动的人设 + R12 引用规则）
2) 历史背景（跨会话摘要）
3) 已知关键事实（槽位）
```

冲突规则写进提示词：**用户最新说法 > 槽位 > 摘要**。这样用户改口说「不是这个订单」时，模型不会死守旧槽位。槽位只用于「不必重复询问」，不能当事实来源做引用（引用仍来自检索资料）。

## 第七章 Step 7（加分）：摘要回写与质量评测

### 7.1 把会话内摘要回写 Go

`SummarizationMiddleware` 生成的摘要只存在 checkpoint 里，后台看不到，也不会进入 `session_summaries`。可选增强：摘要成功后异步 POST 回 Go，刷新跨会话摘要。

实现方式二选一：
- **A（推荐，简单）**：在 `SafeSummarizationMiddleware.abefore_model` 拿到返回值后，从返回的 messages 里找 `lc_source == "summarization"` 的 HumanMessage，异步调用 Go `POST /api/agent/session-summaries` 回写；
- **B**：不改中间件，继续依赖 Go 的 30 分钟空闲任务；缺点是长会话期间后台看不到摘要。

如果做 A，注意：
- 回写必须 `asyncio.create_task` 异步，不能阻塞本轮；
- 回写失败只记日志；
- 不要把摘要写进 `messages` 之外的用户可见内容。

### 7.2 摘要质量抽检

抽 20 组 30 轮会话，人工检查摘要是否保留：
- 订单号 / 工单号（原样，不改写）；
- 商品名、金额；
- 已给出的承诺（时效、退款方式）；
- 用户诉求与是否已转人工。

跨会话摘要的生成 Prompt 在 [session_summary.py](file:///Users/changwenbiao/PycharmProjects/ai_customer_service/python_agent/session_summary.py#L17-L23)，当前是「不超过 80 字、说清诉求/是否解决/是否人工跟进」，**没有要求保留订单号等实体**。建议同步改成：

```python
SUMMARY_PROMPT = """请用不超过 150 字的中文，概括以下智能客服会话。要求：
1. 说清客户的核心诉求、问题是否解决、是否需要人工跟进
2. 必须原样保留：订单号、工单号、商品名、金额、时效承诺（如“48 小时内发货”）
3. 不要编造原文没有的信息
4. 只输出摘要本身，不要任何前缀、标题或解释

会话记录：
{history}"""
```

同时把 `_generate_summary` 里的 200 字截断保留（150 字摘要不会被截），并确认 Go 的 `session_summaries.summary` 是 `TEXT` 类型（当前模型定义就是 `type:text`，无需改表）。

“重要信息可回溯原文”靠两点保证：MySQL `messages` 保留完整原文；槽位保存订单号等强实体。

统计「摘要事实保留率」，目标 ≥ 95%。低于 95% 时，优先加强 `CONTEXT_SUMMARY_PROMPT` 的「必须原样保留」清单，而不是调阈值。

### 7.3 面试口径

> 我不是只加了一个 `trim_messages`。我先用 `token_usage` 的真实 input token 建了 30 轮基线，再把上下文治理拆成三层：工具结果按新旧分级截断、超过软阈值做结构化摘要、超过硬阈值做兜底裁剪。摘要本身可能丢订单号，所以我又做了 Redis 槽位和跨会话摘要注入，并用第 25 轮事实回忆做回归。最后用 token 曲线、TTFT 和成本三项指标证明有效。

## 第九章 上线顺序、开关、回滚、踩坑

### 9.1 上线顺序（每步都可独立回滚）

1. **只加配置和计数**：不挂中间件，先跑 30 轮，校准 `est`；
2. **只挂 `tool_result_guard`**：观察一周，确认工具结果配对正常；
3. **挂 `build_summarization` + `hard_limit_guard`**：重点看触发轮的 TTFT 与摘要质量；
4. **加 Go 摘要接口 + `dynamic_prompt` 注入**：先在测试线程验证，再全量；
5. **加 Redis 槽位**：先只读不写，确认抽取准确，再开启写入；
6. **可选：摘要回写**。

每一步都要保留 `CONTEXT_BUDGET_ENABLED` 开关。

| 出问题 | 回滚动作 |
|---|---|
| 摘要导致回答变差 | `CONTEXT_BUDGET_ENABLED=false`，只保留 `tool_result_guard`（把开关拆成两个更细的 flag 可选） |
| 触发轮 TTFT 过高 | 调高 `CONTEXT_SUMMARY_TRIGGER_TOKENS`，或减小 `CONTEXT_SUMMARY_INPUT_TOKENS` |
| 槽位抽错 | 关闭槽位写入（`CONTEXT_SLOT_ENABLED=false`，若拆了 flag），保留摘要 |
| Go 摘要接口异常 | Agent 端已 try/except，返回空摘要，不影响主流程 |
| 裁剪破坏工具配对 | 只保留 `hard_limit_guard` 的 `trim_messages`（`start_on="human"` 会保护结构） |

### 9.4 踩坑汇总

1. **`count_tokens_approximately` 默认 `chars_per_token=4`，严重低估中文**。必须用自己的计数器，否则摘要永远不触发。
2. **摘要触发轮的 TTFT 会变高**：摘要是一次额外的模型调用。不要把软阈值设得太贴近硬阈值，否则每轮都可能触发。若同步摘要的 TTFT 不可接受，可改成「异步预热」：上一轮结束后判断下一轮是否将超阈值，后台先生成摘要写入 Redis/state，下一轮直接注入；本手册先做同步版，优先保证正确性与可观测。
3. **`keep` 太小会切断上下文**：保留 6 条（约 3 轮）是下限；`keep=0` 会让模型忘记刚说的事。
4. **工具消息替换必须保留 id 和 `tool_call_id`**，否则 `add_messages` 会新增一条而不是替换，反而更膨胀。
5. **摘要中间件失败会抛异常**：必须像 `SafeSummarizationMiddleware` 一样捕获并降级，否则一次限流就打挂整轮。
6. **`dynamic_prompt` 每次模型调用都执行**：里面不要发 HTTP，摘要/槽位要在请求入口准备好。
7. **Go 摘要是「空闲 30 分钟」才生成的**：长会话中途拿不到最新摘要，这是正常的；会话内靠 Step 3 的摘要。
8. **旧摘要会永久不更新**：必须做 4.3 的 `HAVING` 刷新，否则跨会话记忆永远是第一天。
9. **Redis 槽位 TTL 要和 checkpoint 回收期对齐**：都设 7 天，避免「摘要还在、槽位没了」。
10. **不要把用户原文写进日志**：只记录长度和实体数量，避免隐私外泄。
11. **图片/多模态消息**：如果 `content` 是 list 或 base64，`str()` 后可能非常大，工具裁剪管不到 HumanMessage，需要在入口单独限制图片数量。
12. **`CONTEXT_WINDOW_TOKENS` 不要填超过模型真实上限**：裁剪只是省成本，不能突破供应商限制；供应商报错由 R14 处理。
13. **摘要与 R12 引用冲突**：摘要不是资料，不能让模型用摘要里的内容编造 `[n]`。提示词里必须写「历史背景不是检索结果」。
14. **多实例部署**：摘要中间件在各自实例的 checkpoint 上运行，Redis 槽位共享；如果两个实例同时处理同一线程，槽位可能互相覆盖。WebSocket 单线程串行通常不会发生，但要避免 HTTP 并发压测同一线程。

## 附录 C 面试问答

**Q1：为什么不用简单的 `trim_messages` 一刀切？**

答：一刀切会先切掉最早的工具结果，而最早的检索片段往往包含用户问题的答案；同时会切断 AI/Tool 配对。我的顺序是「工具结果按新旧分级压缩 → 摘要压缩 → 硬裁剪」，并且摘要提示词强制保留订单号、金额、承诺等实体，再用 Redis 槽位兜底。

**Q2：摘要本身也会丢信息，怎么办？**

答：三件事：① 摘要 Prompt 明确「原样保留」清单；② 关键实体走规则抽取存 Redis，不依赖模型改写；③ 第 25 轮做事实回忆回归，把「摘要质量」变成可测指标而不是感觉。

**Q3：为什么不直接上向量记忆（如 Mem0）？**

答：当前会话是短周期客服场景，结构化实体 + 摘要足够；引入外部记忆库会增加一次检索延迟和一致性风险。先用最小方案证明 token 降下来、事实不丢，再评估是否需要长期记忆。

**Q4：摘要触发会不会让首 token 延迟翻倍？**

答：会，但只在触发轮。我的做法是把软阈值放在 0.55*window，每 8~10 轮触发一次；触发轮的 TTFT 会升高，下一轮回落。指标上单独统计「触发轮 TTFT」，不把它混进平均值。

**Q5：如何证明不是模型自己记住了，而是你的上下文工程起作用？**

答：做 A/B：同一批 30 轮脚本，一组关闭 `CONTEXT_BUDGET_ENABLED`，一组开启；对比 input token 曲线、TTFT、第 25 轮事实回忆。再单独关掉槽位做消融，证明槽位对事实回忆的贡献。

## 附录 D 与其它需求的衔接

- **R11（检索优化）**：R13 的工具结果截断直接影响检索片段进入上下文的方式；R11 的 chunk 变长后，`TOOL_RESULT_MAX_CHARS` 要同步调整。
- **R12（强制引用）**：摘要和槽位只作为「背景/已知事实」，不能替代检索资料；引用编号仍由本轮检索结果产生。
- **R14（模型调用韧性）**：摘要调用与主调用共享限流；R14 的超时/重试/降级应覆盖摘要调用。R13 的 `SafeSummarizationMiddleware` 是 R14 之前的第一层保护。
- **R15（成本）**：R13 的 token 曲线是成本核算的输入；`token_usage` 已经能按线程、模型汇总。
