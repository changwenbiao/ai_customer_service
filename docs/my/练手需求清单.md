### 需求 3：知识库命中记录补上真实相似度分数（详解版）

**需求**：现在 `kb_hits.score` 大量是 0，因为 `similarity` 检索返回的 Document 没带 score。改成用带分数的检索，把真实相似度存进去。

**涉及技术**：LangChain Retriever/VectorStore API、Qdrant COSINE 相似度、PostgreSQL

#### 背景：这个分数有什么用

`kb_hits` 表是知识库闭环的核心数据——运营靠它回答两个问题：

1. **哪些文档经常被命中？**（列表页 hit_count 排序，已在用）
2. **检索质量怎么样？**（score 分布：命中的分数都很低 → 说明知识库内容跟用户问题对不上，需要补文档；分数高但没解决问题 → 说明文档内容写得不好）

现在第 2 个问题是瞎的，因为 score 全是 0：

```sql
SELECT query, doc_title, score FROM kb_hits ORDER BY id DESC LIMIT 10;
-- 现状：score 列全是 0.0
```

#### 根因分析

现状代码在 [tools.py](../../python_agent/tools.py)：

```python
# search_kb 里（约 L77）
docs = await retriever.ainvoke(query)        # ← 问题在这：retriever 只返回 Document，不带分数

# _record_kb_hits 里（约 L31-36）
rows = [
    (tid, thread_id, d.metadata.get("doc_id", ""), d.metadata.get("title", ""), query,
     float(getattr(d, "metadata", {}).get("score", 0) or 0))   # ← metadata 里根本没有 score 键
    for d in docs
]
```

链条是这样的：

- `retriever = store.as_retriever(search_type="similarity", search_kwargs={"k": 3})`（[agent_factory.py](../../python_agent/agent_factory.py) `get_tenant_retriever`）
- Retriever 的 `ainvoke(query)` 返回 `list[Document]`，**API 设计上就不含分数**（Retriever 的职责是"取回相关文档"，分数被丢弃了）
- 所以 `d.metadata.get("score", 0)` 永远拿到默认值 0

#### 预备知识：tenant_stores 与 tenant_retrievers 是什么关系

它们都是 `app.state` 上的**进程内字典缓存**，键都是 `tenant_id`，但装的东西不同：

```
app.state.tenant_stores     {tenant_id: QdrantVectorStore}   ← 向量库连接本体
app.state.tenant_retrievers {tenant_id: VectorStoreRetriever} ← store 的"预设参数外壳"
```

用一张图看关系和初始化过程：

```
租户第一次聊天
  │
  ▼ get_tenant_agent(app, tenant_id)          [agent_factory.py L429]
  │
  ├─► ensure_tenant_vector(app, tenant_id)    [L69]
  │     │  检查 tenant_stores 有没有 → 有就直接返回（缓存）
  │     │  没有则：
  │     │    1. 拿租户 embedding 模型（BYOK 配置）
  │     │    2. Qdrant 里没有 kb_{tenant} 集合就创建（COSINE，维度自动探测）
  │     │    3. 构建 QdrantVectorStore(client, collection, embedding)
  │     │    4. 存进 tenant_stores[tenant_id] ✅
  │     │  任何一步失败 → 返回 None + 60 秒冷却（对话降级为纯 LLM）
  │     ▼
  ├─► get_tenant_retriever(app, tenant_id)    [L111]
  │     │  检查 tenant_retrievers 有没有 → 有就直接返回（缓存）
  │     │  没有则从 tenant_stores 取 store，包一层：
  │     │    retriever = store.as_retriever(search_type="similarity",
  │     │                                 search_kwargs={"k": 3})
  │     │  存进 tenant_retrievers[tenant_id] ✅
  │     ▼
  └─► create_agent(...) 建租户 Agent，存进 tenant_agents[tenant_id]
```

一句话：**store 是"连接"，retriever 是"带着 k=3 参数的连接快捷方式"**。`retriever.ainvoke(query)` 等价于 `store.asimilarity_search(query, k=3)`，retriever 没有额外能力。

**失效与重建**（这是本需求要改代码时必须知道的）：

- 知识库任何变更（删除/重索引/批量/手动入队）后，代码都会执行 `tenant_retrievers.pop(tenant_id, None)`——因为集合内容变了，想让下次检索用新的
- 重建是**懒触发**的：下一次该租户聊天时，`get_tenant_agent` 会兜底检查 `tenant_id not in tenant_retrievers` 就重建（这个兜底是刚修过的 Bug，之前 pop 之后永远不重建，检索会卡死在「知识库暂未就绪」）
- `tenant_stores` 只在进程重启或模型配置变更时清——删文档**不需要**重建 store（连接还是同一个，只是里面的向量少了）

**对本需求的意义**：因为要拿分数，我们要**绕过 retriever 直接调 store**。所以改造后 `tenant_retrievers` 这条线对 search_kb 就没用了（`ensure_tenant_vector` 建的 store 才是我们要的）。

#### 改造方案

**第 1 步：改用带分数的 API**

`QdrantVectorStore` 本体有 `asimilarity_search_with_score(query, k=...)`，返回 `list[(Document, score)]`。不再走 retriever，直接拿 store：

```python
# tools.py search_kb 中，把原来的：
#   retriever = _app.state.tenant_retrievers.get(tid)
#   if retriever is None: return "知识库暂未就绪，请稍后再试。"
#   docs = await retriever.ainvoke(query)
# 改为：

from config import RETRIEVER_TOP_K

store = _app.state.tenant_stores.get(tid)     # 注意：换 tenant_stores，不是 tenant_retrievers
if store is None:
    return "知识库暂未就绪，请稍后再试。"
try:
    docs_with_scores = await store.asimilarity_search_with_score(query, k=RETRIEVER_TOP_K)
except Exception as e:
    _logger.warning(f"[KB Degrade] tenant={tid} 检索失败，降级为纯LLM: {str(e)[:150]}")
    return "知识库暂未就绪，请稍后再试。"
docs = [doc for doc, _score in docs_with_scores]   # 拼装回答文本用
```

> 顺带思考：改了之后 `tenant_retrievers` 缓存就没用了。保留它还是删掉？各有什么影响？（提示：retriever 是 store 的轻量包装，删了无功能损失，但要确认没有别处调用 `get_tenant_retriever`——grep 一下）

**第 2 步：搞清楚 score 的语义（重要，别想当然）**

项目 Qdrant 集合用的是 `Distance.COSINE`（`ensure_tenant_vector` 里创建）。Qdrant 的 COSINE 返回的是**余弦相似度**：**越大越相似**，范围大致 [-1, 1]，常见命中在 0.5~0.9。

动手前先用 API 验证一下真实分布，别猜：

```bash
# 先正常聊几句产生向量，然后直接查 Qdrant 看分数
curl -s -X POST localhost:6333/collections/kb_t_demo/points/scroll \
  -H 'Content-Type: application/json' \
  -d '{"limit": 3, "with_payload": true, "with_vector": true}' 
# 拿到一个向量后，用它 search 看 score 值长什么样（也可做完第 1 步后直接看 kb_hits 数据）
```

**第 3 步：改造 `_record_kb_hits` 接收分数**

函数签名从收 `docs` 改为收 `docs_with_scores`：

```python
async def _record_kb_hits(tid: str, thread_id: str, query: str, docs_with_scores: list) -> None:
    try:
        if docs_with_scores:
            rows = [
                (tid, thread_id,
                 d.metadata.get("doc_id", ""), d.metadata.get("title", ""), query,
                 float(score))                      # ← 真实的相似度
                for d, score in docs_with_scores
            ]
        else:
            rows = [(tid, thread_id, "", "", query, 0.0)]
        # ... executemany 不变
```

`kb_hits.score` 字段是 `REAL`（init.sql 已定义），不用改表。

**第 4 步：保持原有降级行为不变（检查清单）**

- [ ] store 为 None → 返回「知识库暂未就绪，请稍后再试。」
- [ ] 检索异常 → warning 日志 + 同样的提示语，**不抛穿对话**
- [ ] 无结果 → 「未找到相关信息，建议转接人工客服。」+ 落一条空 doc_id 的未命中记录
- [ ] 缓存读写逻辑（`_kb_cache_get/_set`）不变
- [ ] 返回给模型的文本格式不变（`"\n".join(f"- {doc.page_content}")`）

## L2 进阶级（跨服务改动，需要理解链路）

### 需求 4：知识库变更后立刻失效检索缓存（修一致性缺陷）（详解版）

#### 背景

`search_kb` 的检索结果有进程内缓存（[cache.py](../../python_agent/cache.py)），同一个租户问同一个问题，TTL 内直接返回缓存答案。但**知识库内容变了，缓存不会变**：

- 删掉一篇文档 → 最长 TTL 时间内，用户还能问到这篇文档里的内容（已删除信息泄露）
- 重索引一篇修改过的文档 → TTL 内用户拿到的还是旧版答案
- 管理端「命中明细/最近命中」统计也会失真（缓存命中不走检索、不写 `kb_hits`，这是另一个已知行为）

TTL 越长性能越好、一致性越差；TTL 越短则相反（你之前把 TTL 改成 10s 调试，就是把这个矛盾缩小到了 10 秒）。**正确做法不是靠短 TTL，而是变更时主动失效缓存**——性能和一致性兼得。

#### 根因分析

现状缓存模块（[cache.py](../../python_agent/cache.py)，全文仅 52 行）：

```python
# key: "tenant_id:query_hash", value: (expire_time, result)
_kb_cache = {}

def _kb_cache_key(tenant_id: str, query: str) -> str:
    q_hash = hashlib.md5(query.strip().lower().encode('utf-8')).hexdigest()
    return f"{tenant_id}:{q_hash}"          # ← key 自带租户前缀，这是能按租户清理的关键

def clear_kb_cache():
    """清空全部缓存（模型/向量配置变更时调用）"""
    _kb_cache.clear()                        # ← 只有"全清"，没有"按租户清"
```

问题有两个：

1. **没有按租户清理的函数**——`clear_kb_cache()` 只能全清，而 KB 变更只影响一个租户，全清会误伤其他租户的热缓存
2. **KB 变更的代码路径根本没调用任何清理**——[routers_kb.py](../../python_agent/routers_kb.py) 的删除/重索引/批量接口只做了 Qdrant 删向量、DB 删记录、（改造前）pop retriever，从未碰 `_kb_cache`

#### 预备知识：什么时刻算"知识库变了"

这是本需求最容易做错的地方——**不是每个接口调用时都该清缓存**，要看向量内容什么时候真正变化：

| 操作 | 向量何时变化 | 该在何处清缓存 |
|---|---|---|
| 上传文档（status=0 待索引） | 还没建向量 | ❌ 不用清 |
| 删除文档 / 批量删除 | 接口里**立即**删了 Qdrant 向量 | ✅ 接口里立即清 |
| 重索引 / 批量重索引 | 接口里先删旧向量，worker **异步**写新向量 | ✅ 接口里清（删旧）+ worker 完成时清（写新）|
| 手动入队 `/kb/index` | 入队时不变，worker 完成才变 | ✅ worker 完成时清 |
| worker 索引成功（status=1） | 新向量此刻生效 | ✅ [kb_index_worker.py](../../python_agent/kb_index_worker.py) `_index_one` 成功分支 |

关键点：**worker 和 FastAPI 在同一个进程**（`main.py` lifespan 里 `asyncio.create_task(index_worker_loop(...))` 启动），所以 worker 可以直接调 `cache.py` 的函数操作同一个 `_kb_cache` 字典，不需要跨进程通信。

#### 改造方案

**第 1 步：cache.py 加按租户清理函数**

```python
def clear_kb_cache(tenant_id: str | None = None):
    """清空知识库检索结果缓存。
    tenant_id 为 None → 全清（模型/向量配置变更时用）；
    指定 tenant_id → 只清该租户（KB 文档变更时用，不误伤其他租户）。
    key 格式为 "tenant_id:md5(query)"，按前缀匹配。
    """
    if tenant_id is None:
        n = len(_kb_cache)
        _kb_cache.clear()
        return n
    prefix = f"{tenant_id}:"
    keys = [k for k in _kb_cache if k.startswith(prefix)]
    for k in keys:
        del _kb_cache[k]
    return len(keys)
```

**第 2 步：在变更点调用**（对照上面的时机表）

- `routers_kb.py` `kb_delete`：删完向量/记录后调 `clear_kb_cache(tenant_id)`
- `routers_kb.py` `kb_reindex`：删完旧向量后调（别等 worker，中间窗口期旧答案必须失效）
- `routers_kb.py` `kb_batch`：`delete` 和 `reindex` 两个分支都要调
- `kb_index_worker.py` `_index_one`：UPDATE status=1 成功后调（`clear_kb_cache` 是同步函数，直接调，别用 await）

调用处加一行日志 `logger.info("KB cache invalidated tenant=%s n=%d", tenant_id, n)`，方便验收时观察。

**第 3 步：检查遗漏**

`grep -rn "clear_kb_cache" python_agent/`，确认所有「会改向量内容」的路径都覆盖了；再反向确认「只改元数据不改向量」的操作（比如单纯改分类 `category`）**没有**误清——改分类不影响检索内容，清了是浪费。

#### 验收

```bash
docker compose up -d --build agent
```

1. 上传一篇文档（内容包含一个独特事实，如"本平台的吉祥物是蓝色大象"）→ 索引 → 聊天问"吉祥物是什么"，得到答案 A
2. 删除该文档
3. **立刻**再问同样的问题 → 答案不能再是 A（缓存命中会直接返回旧答案 A，失效成功则会走真实检索返回"未找到相关信息"）
4. 重索引场景同理：改文档内容 → 重索引 → 等 status=1 → 再问，必须是新答案
5. 看日志里 `KB cache invalidated` 的触发次数和时机是否符合预期

#### 扩展思考

1. **多实例部署怎么办**：本项目只跑一个 agent 容器，进程内清理够用。如果将来水平扩容，单实例清缓存其他实例不知道——项目已有现成的 Redis 广播机制（[redis_pubsub.py](../../python_agent/redis_pubsub.py) 的 `invalidate_listener`，现在用于模型配置失效广播），模仿它加一种 `kb_cache` 消息类型即可，这也是需求 10 的前置。
2. **重索引窗口期的行为**：reindex 接口清缓存后、worker 写完新向量前，用户提问会得到"未找到相关信息"。这比返回旧答案好（一致性优先），但你能不能接受？能不能做得更好（比如保留旧向量直到新向量写完再切换）？
3. **清缓存的粒度**：现在是"文档一变就清整个租户"。如果租户有 1000 篇文档只改了 1 篇，全部查询缓存失效会不会太狠？更细粒度需要知道"哪些 query 命中过这篇文档"——`kb_hits` 表里有 query 和 doc_id 的对应关系，理论上能反推，值得吗？

### 需求 5：工单 SLA——人工超时未响应自动提醒（详解版）

#### 背景

用户点「转人工」后创建工单进入 `pending`（待接管）状态。如果客服不在线或没看到，用户就干等着——没有任何反馈，也不知道还要等多久。这是真实客服系统最常见的投诉点。

SLA 提醒要解决的问题：**工单 pending 超过阈值（比如 10 分钟）还没人接管时，系统主动安抚用户**（WS 推一条系统消息），同时（可选）提醒在线客服/在管理端标红。

#### 现状梳理（读代码确认过的事实）

**工单表**（[init.sql](../../deploy/init/mysql/init.sql) L91-112，MySQL 库）：

```sql
tickets: id, thread_id, ticket_no, user_id, reason,
         status tinyint  -- 0待处理 1接管中 2已取消 3已关闭
         priority tinyint -- 0低 1中 2高 3紧急
         created_at, closed_at, tenant_id, handler_uid, handler_name, deleted_at
-- 关键索引：idx_tickets_tenant_status_time (tenant_id, status, created_at)
--          ↑ 这个索引正好支持"查某租户 status=0 且 created_at 早于 X"的 SLA 扫描
```

**状态机**：`pending(0) → handling(1) → closed(3)`，另有取消 `canceled(2)`。切换入口在 [store.go](../../go_service/internal/repository/store.go) `UpdateTicketStatus`（L279），每次变更写 `ticket_logs`（`AddTicketLog` L290）。

**WS 推送结构**（[hub.go](../../go_service/internal/pkg/ws/hub.go)）：Hub 里 `users map[string]*Client`（按 userID 推用户）、`admins map[*Client]bool`（广播客服）。给用户推消息的写法参考 [ws.go](../../go_service/internal/handler/ws.go) 里 `onChunk` 回调怎么把 AI token 推给用户的——SLA 提醒只是换一种消息类型走同一条路。

**已有定时任务范例**：[main.go](../../go_service/main.go) L77-79 已经有一个 `time.NewTicker(1 * time.Hour)` 的 goroutine（会话清理用），照抄这个模式即可。

#### 预备知识：这个功能的三个设计决策

1. **扫描式 vs 定时器式**：每个工单创建一个 `time.AfterFunc` 定时器？还是一个 ticker 每分钟扫一次表？工单量小但定时器要处理进程重启丢定时器的问题；**扫描式更简单且天然抗重启**（状态在 DB 里），选扫描。
2. **幂等（不重复提醒）**：ticker 每分钟扫到同一张超时会工单，不能每分钟都推消息。需要一个「已提醒」标记——两种做法：
   - `tickets` 加字段 `sla_reminded_at datetime`（改表，直白）
   - 不加字段，查 `ticket_logs` 里是否已有 `action='sla_remind'` 的记录（不改表，但每次多一次查询）
   建议加字段，顺便在工单详情里能展示「何时提醒过」。
3. **提醒谁**：用户（WS 系统消息）必须；客服（遍历 `admins` 广播）可选。注意用户可能已断连——`users[userID]` 查不到就跳过，消息不落地还是落库一条「系统消息」让用户重连后能看到？这是你要做的取舍（落库更完整，参考 `SaveTicketMessage`）。

#### 改造方案

**第 1 步：改表**（在 [init.sql](../../deploy/init/mysql/init.sql) tickets 定义加字段，已有库需要手动 ALTER）

```sql
ALTER TABLE tickets ADD COLUMN sla_reminded_at datetime(3) DEFAULT NULL COMMENT 'SLA超时提醒时刻';
```

**第 2 步：repository 加两个函数**（[store.go](../../go_service/internal/repository/store.go)）

```go
// 扫描超时未提醒的 pending 工单（命中 idx_tickets_tenant_status_time 索引）
func ListSlaTimeoutTickets(timeout time.Duration) ([]model.Ticket, error)
// SQL: WHERE status = 0 AND deleted_at = 0 AND sla_reminded_at IS NULL
//      AND created_at < NOW() - INTERVAL ? SECOND

// 标记已提醒（带条件更新防并发重复：AND sla_reminded_at IS NULL）
func MarkSlaReminded(ticketID uint64) (bool, error)
```

`MarkSlaReminded` 返回「这次是不是我标记成功的」——用 `RowsAffected` 判断，并发扫描时只有一个扫描者能标记成功，只有它去发消息，彻底防重。

**第 3 步：SLA 扫描 goroutine**（`go_service/internal/service/` 新建文件）

```go
func StartSlaMonitor(hub *ws.Hub) {
    timeout := 10 * time.Minute // 做成 env：TICKET_SLA_MINUTES
    ticker := time.NewTicker(1 * time.Minute)
    for range ticker.C {
        tickets, _ := repository.ListSlaTimeoutTickets(timeout)
        for _, t := range tickets {
            ok, _ := repository.MarkSlaReminded(t.ID)
            if !ok { continue } // 已被别的扫描标记过
            // 给在线用户推系统消息（userID → hub.users）
            // 可选：AddTicketLog(action="sla_remind") + 广播 admins + priority 提到 2
        }
    }
}
```

在 `main.go` 启动时调用（参考 L77 现有 ticker 的位置）。

**第 4 步：消息格式**。WS 消息协议的 msg type 参考现有 AI 回复/系统消息的 type 定义（看 ws.go 里 onChunk/onEnd 推的 JSON 结构），前端收到后渲染成系统气泡。**先在浏览器 DevTools 的 WS 面板看一条真实消息长什么样，再定你的 SLA 消息格式**。

#### 验收

```bash
# 把超时时间调短方便测试：TICKET_SLA_MINUTES=1
```

1. 用户端聊天 → 触发转人工 → 产生 pending 工单
2. 不接管，等 1~2 个扫描周期 → 用户端收到「客服繁忙」系统消息
3. 再等 5 分钟 → **不能**收到第二条（幂等）
4. 客服接管（status→1）→ 之后永远不提醒
5. SQL 验证：`SELECT id, status, sla_reminded_at FROM tickets ORDER BY id DESC LIMIT 3;`

#### 扩展思考

1. **用户已断连时消息丢不丢**：hub 里查不到 userID 就直接跳过了——用户重连后看不到提醒。要不要落库（`SaveTicketMessage` 存一条 role=system）让历史消息能带出它？
2. **提醒升级**：第一次提醒后如果 30 分钟还没接管，要不要二次提醒 + priority 升到 3（紧急）？现在的设计加一个字段就能支持（想想加什么）。
3. **多实例问题**：如果 go_service 扩容到 2 个副本，两个 ticker 同时扫——`MarkSlaReminded` 的条件更新（`AND sla_reminded_at IS NULL` + RowsAffected）已经解决了并发重复，理解这一点就理解了「用 DB 原子操作做分布式锁」的思想。
4. **管理端标红**：前端工单列表接口 `ListTickets`（store.go L227）返回的数据里加 `sla_timeout` 计算字段（`status=0 && now-created_at > 阈值`），前端标红——纯查询时计算，不用改表。

### 需求 6：业务指标进 Prometheus（P3-4 收尾）（详解版）

#### 背景

现在的监控只回答了「服务活着吗、接口快不快」，回答不了「业务跑得怎么样」：

- 今天有多少条用户消息、AI 回了多少条？
- 转人工了多少次？转人工率是升高还是降低？
- 哪个租户在用、哪个租户快流失了？
- 上了新 Prompt / 新知识库之后，转人工率有没有下降（效果验证）？

这三类指标（消息量、工单量、转人工次数）是运营和排障最常看的数据，但它们现在**完全没有埋点**。[prometheus.yml](../../deploy/observability/prometheus.yml#L14-L21) 只抓 Go 的 `/metrics`，而 Go 里只有 6 个技术指标（[metrics.go](../../go_service/internal/middleware/metrics.go#L13-L67)）：

```
cs_http_requests_total            请求数（method/path/status）
cs_http_request_duration_seconds  请求延迟（method/path）
cs_websocket_connections          WS 连接数
cs_active_sessions                活跃会话数
cs_agent_calls_total              Agent 调用次数（endpoint/status）
cs_agent_call_duration_seconds    Agent 调用延迟（endpoint）
```

全是「基础设施指标」，没有一条体现业务行为。

#### 现状梳理（读代码确认过的事实）

**指标怎么暴露到 Prometheus**（三个环节，缺一不可）：

```
metrics.go 用 promauto 注册指标（全局变量，包初始化即注册到默认 Registry）
      ↓
router.go:58  r.GET("/metrics", gin.WrapH(promhttp.Handler()))   ← 暴露为 HTTP 文本
      ↓
prometheus.yml 每 15s 抓 go:8080/metrics（retention 7d）
      ↓
Grafana（datasource uid=prometheus）读 Prometheus 画图
```

- 现有写法有一套固定模式：指标变量私有（小写开头）+ 导出的 helper 函数（如 `IncWSConnections()`、`IncAgentCalls(endpoint, success)`），业务代码只调 helper，不直接碰 `WithLabelValues`——**加新指标必须沿用这个模式**
- `/metrics` 已被 [status_code.go](../../go_service/internal/middleware/status_code.go#L86) 的状态码归一化中间件跳过，不用额外处理
- Prometheus/Grafana 属于 `profiles: ["observability"]`，不带 profile 启动时不会运行

**消息落库的全部位置**（这就是消息量的埋点位置，漏一个通道数据就不准）：

| 通道 | 位置 | role |
|---|---|---|
| WS 用户发消息 | [ws.go](../../go_service/internal/handler/ws.go#L124) L124 / L144 | `user` |
| WS AI 回复结束 | [ws.go](../../go_service/internal/handler/ws.go#L196-L205) `onEnd` | `ai`（人工接管中则是 `ai` 归属工单） |
| HTTP 用户消息 | [chat.go](../../go_service/internal/pkg/chat/chat.go#L28) | `user` |
| HTTP AI 回复 | [chat.go](../../go_service/internal/pkg/chat/chat.go#L112-L114) | `ai` |
| 人工客服发消息 | [ticket_service.go](../../go_service/internal/service/ticket_service.go#L249) | `human` |
| 系统提示（已接管/结束/转交） | ticket_service.go L227/L278/L326/L349 | `system` |

**工单创建的全部位置**（两个通道，都走同一个 `EnsureTicket`）：

- [ws.go](../../go_service/internal/handler/ws.go#L220) `onInterrupt` 回调
- [chat.go](../../go_service/internal/pkg/chat/chat.go#L78) HTTP 通道

`EnsureTicket` 返回 `(ticket, reused, err)`，**`reused=true` 表示复用已存在的未关闭工单**——这里是最容易把工单量算重的地方。

**租户怎么拿到**：`auth.TenantFromUserID(userID)`（[auth.go](../../go_service/internal/pkg/auth/auth.go#L279)），或 [store.go](../../go_service/internal/repository/store.go#L23-L33) 从 `thread_id` 前缀提取。

#### 预备知识：三个必须先想清楚的设计决策

**① 为什么 thread_id / user_id 绝对不能当 label**

Prometheus 的一个 label 组合 = 一条独立的时间序列（series），每个 series 在内存里要占一块固定大小的 chunk。假设按 `{tenant_id, thread_id}` 打点：1000 个活跃会话 = 1000 条 series，且每次新用户进来都**永久新增**一条（即使之后不再增长）。行业经验是单个指标超过几千条 series 就会拖慢查询、爆内存。

所以 label 只放**取值有限且枚举稳定**的维度：

| label | 可用？ | 理由 |
|---|---|---|
| `tenant_id` | ✅ | 租户数量有限（几十~几百） |
| `role` | ✅ | 固定 4 值：user/ai/human/system |
| `action` | ✅ | 固定 2 值：created/closed |
| `thread_id` | ❌ | 无上限，等于把 Prometheus 当明细数据库用 |
| `user_id` | ❌ | 同上 |
| `msg_content` / `path` 带参数 | ❌ | 同上（现有 code 已经用 `URL.Path` 而非 full URL，就是为这个） |

需要按会话/用户钻取明细，那是**日志（Loki）**和**DB** 的职责，不是指标的职责。这是监控系统最重要的一条分工原则。

**② 「转人工次数」和「工单创建数」不是一回事**

一次转人工请求可能复用已有工单（`reused=true`），此时用户看到的是「已提交人工客服，工单号：xxx」（同一个单号）。那么：

- `cs_transfer_to_human_total`：**每次 interrupt 都 +1**（表示"用户想转人工的意愿次数"）
- `cs_tickets_total{action="created"}`：**只在 `!reused` 时 +1**（表示"真正新建的工单数"）

两者之差 = 复用的次数。转人工率的分母应该是用户消息量：

```
转人工率 = rate(cs_transfer_to_human_total[1h]) / rate(cs_messages_total{role="user"}[1h])
```

如果只埋其中一个，你算出来的率会失真。**想清楚语义再动手，比写完再改省事。**

**③ CounterVec 在第一次 WithLabelValues 之前不存在**

`promauto.NewCounterVec` 注册的是「指标族」，但 `/metrics` 输出里**不会出现任何 series**，直到第一次调用 `WithLabelValues(...).Inc()`。所以验收时「curl 看不到 cs_messages_total」很可能不是代码错，而是**还没产生过消息**。先聊一轮再 curl。

#### 改造方案

**第 1 步：metrics.go 加三个指标 + helper**（沿用现有模式）

```go
// 业务指标（P3-4 收尾）
var (
    messagesTotal = promauto.NewCounterVec(
        prometheus.CounterOpts{
            Name: "cs_messages_total",
            Help: "Total messages by role",   // 注意：Help 写清语义，Grafana 里能直接看到
        },
        []string{"tenant_id", "role"},        // ← 顺序必须与 WithLabelValues 一致，错位会 panic
    )
    ticketsTotal = promauto.NewCounterVec(
        prometheus.CounterOpts{Name: "cs_tickets_total", Help: "Total tickets"},
        []string{"tenant_id", "action"},
    )
    transferTotal = promauto.NewCounterVec(
        prometheus.CounterOpts{Name: "cs_transfer_to_human_total", Help: "Transfer to human requests"},
        []string{"tenant_id"},
    )
)

func IncMessages(tenantID, role string) {
    messagesTotal.WithLabelValues(tenantID, role).Inc()
}
func IncTickets(tenantID, action string) { // action: "created" / "closed"
    ticketsTotal.WithLabelValues(tenantID, action).Inc()
}
func IncTransferToHuman(tenantID string) {
    transferTotal.WithLabelValues(tenantID).Inc()
}
```

命名约定注意：计数器必须以 `_total` 结尾（Prometheus 规范），Grafana/告警里的函数（`rate`）依赖这个后缀去识别 counter。

**第 2 步：在落库点旁边埋点**（不是替换落库，是并行加一行）

消息（`ws.go` L124/L144/L200、`chat.go` L28/L114、`ticket_service.go` L249/L227）：

```go
_ = repository.SaveMessage(userID, "user", msg.Msg, msg.MsgType)
middleware.IncMessages(auth.TenantFromUserID(userID), "user")
```

⚠️ 两处 `SaveMessage` 内部会 `return nil` 跳过空 content（[store.go](../../go_service/internal/repository/store.go#L35-L37)）——埋点如果放在"落库成功"之后，空消息不会计数，这通常是**期望行为**；如果想统计空消息，就放在调用前。**自己决定，但要在注释里写清。**

工单（`ws.go` L227 `!reused` 分支、`chat.go` L78 之后）：

```go
if !reused {
    middleware.IncTickets(auth.TenantFromUserID(userID), "created")
}
```

关闭/取消/结束的工单（`ticket_service.go` `CloseTicket`/`CancelTicket` 附近）加 `IncTickets(tenantID, "closed")`——**注意 CLOSED 与 CANCELED 要不要都算 closed 是业务决策**，建议单独 action 值（`closed`/`canceled`）更清楚。

转人工（`ws.go` `onInterrupt` 回调开头、`chat.go` 同位置）：

```go
middleware.IncTransferToHuman(auth.TenantFromUserID(userID))
```

**第 3 步：Grafana 加面板**

[dashboards/customer-service-overview.json](../../deploy/observability/grafana/dashboards/customer-service-overview.json) 是一个固定结构的 JSON：`panels[]` 里每个 panel 有 `id / type / title / gridPos / targets[].expr / datasource.uid`。新增 panel 时：

- `id` 不重复（现有用到 1~6）
- `gridPos` 的 `y` 排在最下面，`w:12 h:8` 两个一排
- `datasource.uid` 必须是 `prometheus`（provisioning 里定义的 uid，见 [datasources 配置](../../deploy/observability/grafana/provisioning/datasources/)）

三个面板的 PromQL：

```promql
# 消息量（按角色）
sum by (role) (rate(cs_messages_total[5m]))

# 工单量（创建 vs 关闭）
sum by (action) (increase(cs_tickets_total[1h]))

# 转人工率
sum(rate(cs_transfer_to_human_total[1h])) / sum(rate(cs_messages_total{role="user"}[1h]))
```

**第 4 步（可选）：加告警规则**

[alerts.yml](../../deploy/observability/alerts.yml) 已有两个规则（服务掉线、5xx 过高）。可以加：

```yaml
- alert: HighTransferRate
  expr: sum(rate(cs_transfer_to_human_total[10m])) / sum(rate(cs_messages_total{role="user"}[10m])) > 0.3
  for: 10m
```

意义：转人工率异常升高通常意味着 AI 答不上来（知识库缺失 / 模型故障 / Prompt 回归）。

#### 验收

```bash

```

   ```bash

   ```
   应该看到 4 种 role 的 series（至少 user/ai 有值）
2. **靶点状态**：`http://localhost:9090/targets` → `go-service` UP
3. **Prometheus 查询**：在 Graph 页输入 `sum by (role)(rate(cs_messages_total[5m]))`，曲线随时间增长
4. **Grafana**：`http://localhost:3000`（admin/admin123）→ 看板「智能客服系统 - 总览」出现新面板
5. **端到端**：聊 3 轮 + 触发一次转人工 → `cs_transfer_to_human_total` +1、`cs_tickets_total{action="created"}` +1；再说一次转人工（复用未关闭工单）→ 只有 `transfer_total` +1，`created` 不变 ← **这是验证第 ② 条设计决策的关键用例**

#### 扩展思考

1. **`deploy/observability/` 被 gitignore 了**（`.gitignore:13`，实测 `git check-ignore` 命中）——你的面板 JSON 改动不会进版本库，别人 clone 下来看不到。要么把 dashboards 目录单独纳入版本管理，要么把面板导出的 JSON 放进 docs。想清楚为什么原作者要 ignore 这个目录（提示：里面有 admin 密码？看 [docker-compose.yaml](../../docker-compose.yaml#L320-L323) 的 env 默认值）。
2. **Go 埋点和 Python 侧指标不一致**：消息真正是 Agent 生成的，Go 只是转发。如果要统计「LLM 首 token 延迟 / token 消耗 / 检索耗时」，只能从 Python 侧埋——要么让 agent 也暴露 `/metrics`（Python 用 `prometheus_client`），要么让 Go 在 SSE 事件里回传达（`prometheus.yml` 加一个 job）。这是需求 6 的天然延伸。
3. **`increase` vs `rate`**：`rate` 适合 QPS（每秒），`increase` 适合「这段时间内涨了多少次」。面板里用错会差一个系数（5m vs 5m×60）。
4. **多实例聚合**：go_service 若扩到 2 副本，两个实例各自有一份 Counter，`/metrics` 会带 instance label 区分——PromQL 里必须 `sum(...)` 聚合，否则 Grafana 画两条线。现在单实例看不出这个问题，但写 `sum by` 是好习惯。
5. **指标语义 vs 数据一致性**：埋点如果在 DB 写完之前执行，DB 失败会造成"指标涨了但消息丢了"；反过来则可能"消息在但指标漏了"。这类偏差在告警阈值上会被放大——思考一下你的埋点该放在事务内还是事务外。

### 需求 7：知识库文档「测试问答」功能（P3-2 之一）（详解版）

> 本需求已实现，代码见下文「改造成果」；下面保留完整的分析与设计过程，方便复习。

#### 背景

知识库的整条链路是黑的：上传 → 手动索引 → 分片 → embedding → 写 Qdrant → 检索。运营上传一份文档后，**唯一能验证「有没有生效」的手段是去聊天窗口问 AI**。但那样有两个问题：

1. **中间多了一层大模型**：AI 答不出来，你分不清是「检索没召回」还是「召回了但模型没答好」。排查方向完全不同。
2. **看不到分数**：模型只会给你一段人话，你无法判断召回质量是 0.9（高度相关）还是 0.4（勉强沾边）。
3. **污染数据**：为了测试而聊天，会写 `kb_hits`、写会话消息、消耗 token，指标被测试数据污染。

「测试问答」要提供的正是**绕过 LLM 的裸检索视图**：输入问题 → 直接看到 Top-K 分片原文 + 真实相似度分数 + 来自哪篇文档。运营一眼就能判断：

- 召回对了、分数高 → 文档没问题，AI 答不好是 Prompt/模型的事
- 召回错了/没召回 → 文档没索引、分片不合理、或内容本身没写到

#### 现状梳理（读代码确认过的事实）

**要复用的三块现成能力**：

| 能力 | 位置 | 说明 |
|---|---|---|

#### 预备知识：四个设计决策

**① 为什么不走 `search_kb` 工具**

`search_kb` 是给大模型用的，它做了三件测试接口不需要的事：查/写 10 秒缓存、写 `kb_hits`、把结果格式化成 `"- 内容"` 的字符串（丢掉分数和 metadata）。测试接口要求「每次都是真实检索、不改动任何业务数据」，所以必须独立实现，**不能复用工具函数**。

**② 用哪个租户的 embedding**

必须用**当前登录用户所属租户**的（`tenant_from_request`），不是平台默认的。原因：租户可 BYOK 自己的 embedding 模型，平台 embedding 和租户 embedding 的向量空间不同——用错模型算出来的相似度没有意义。`ensure_tenant_vector(app, tenant_id)` 内部已经调 `get_tenant_embeddings(app, tenant_id)`，直接用即可。

**③ 首次调用会自动建集合，这是特性**

`ensure_tenant_vector` 在集合不存在时会 `create_collection` + 维度探测。所以这个接口可以在**从未聊过天的新租户**上直接调用——上传第一份文档、索引完就能测，不必先聊一轮触发建集合。副作用：如果该租户文档全是 `status=0`（未索引），返回 0 条命中——这正确反映"向量库里确实没有内容"。

**④ k 的上限保护**

`RETRIEVER_TOP_K=3` 是聊天用的经验值，测试时运营可能想多看点（5/10）。但**不能让前端随便传 1000**——一次拉太多分片会放大 embedding 和 Qdrant 的开销，也淹没有效信息。接口里 `max(1, min(k, 10))` 钳制在 1~10。

#### 改造成果（已实现，可直接对照）

**第 1 步：Python 后端**（[routers_kb.py](../../python_agent/routers_kb.py#L419-L457)）

```python
@router.post("/agent/kb/test-query")
async def kb_test_query(request: Request):
    tenant_id = tenant_from_request(request)
    body = await request.json()
    query = (body.get("query") or "").strip()
    if not query:
        return {"code": 400, "msg": "query 不能为空"}
    k = max(1, min(int(body.get("k") or RETRIEVER_TOP_K), 10))

    store = await ensure_tenant_vector(request.app, tenant_id)
    if store is None:
        return {"code": 503, "msg": "向量模型/向量库不可用，请检查租户模型配置"}
    pairs = await store.asimilarity_search_with_score(query, k=k)

    items = [{
        "doc_id": doc.metadata.get("doc_id", ""),
        "title": doc.metadata.get("title", ""),
        "score": float(score),
        "content": doc.page_content,
    } for doc, score in pairs]
    return {"code": 0, "data": {"query": query, "k": k, "count": len(items), "items": items}}
```

三个细节值得注意：

- `request.json()` 包了 `try`（非法 JSON 返回 400 而不是 500）
- `k` 转换包了 `try`（前端传字符串/乱值不炸）
- `store` 为 `None` 返回 **503**（依赖不可用，不是参数错误）——HTTP 语义上 4xx=你错、5xx=我错

**第 2 步：Go 代理**（[router.go](../../go_service/internal/router/router.go#L196-L199)）

```go
biz.POST("/kb/test-query", middleware.RequirePerm(permission.KnowledgeView), func(c *gin.Context) {
    handler.ProxyToAgent(c, http.MethodPost, "/agent/kb/test-query")
})
```

权限用 `KnowledgeView`（只读），不是 `KnowledgeEdit`——测试不改变任何状态，给"只能看"的运营角色也能用。`ProxyToAgent` 会自动带上 `X-Tenant-Id`（`middleware.TenantOf(c)`），这是租户隔离不漏的关键。

**第 3 步：前端**（[Knowledge.vue](../../admin-app/src/views/Knowledge.vue#L131-L169)）

- 页头 L21 加「测试问答」按钮（无 `v-perm`，页面本身已有访问权限门槛）
- 弹窗：问题输入框（Ctrl+Enter 快捷检索）+ Top-K 下拉（3/5/10）+ 结果卡片
- 结果卡片每个分片显示：序号、文档标题、`score 0.812` 徽标（按分数配色：≥0.75 绿 / ≥0.5 黄 / 其他红）、分片原文（可滚动）
- 未命中时显示明确的排查提示（"请确认文档已索引"），而不是空白

**第 4 步：不要做的事（刻意省略）**

- ❌ 不写 `kb_hits`：测试行为不该污染命中统计
- ❌ 不走缓存：测试必须每次真实检索，否则改完文档看到旧结果
- ❌ 不调 LLM：这正是本需求的核心价值

#### 验收

```bash
docker compose up -d --build agent go    # 后端
# 前端：admin-app 构建/热更新（按你们的启动方式）
```

1. 上传一份含「退款政策」的文档 → 点「开始索引」→ 等状态变「已索引」
2. 管理端点「测试问答」→ 输入「怎么退款」→ 应看到 1~3 条分片，`score` 在 0.6~0.95 区间，标题是那篇文档
3. 输入一个与文档无关的问题（如「今天天气」）→ 应看到低分分片（~0.3）或 0 条
4. 上传一份**不索引**的文档 → 它的内容一定检索不到（验证"未索引不参与检索"）
5. 直接调接口验证返回结构：
   ```bash
   curl -s -X POST localhost:8080/api/admin/kb/test-query \
     -H "Authorization: Bearer <token>" -H "Content-Type: application/json" \
     -d '{"query":"怎么退款","k":5}' | jq
   ```
6. 查 `kb_hits` 确认**没有新增记录**（测试不该污染统计）

#### 扩展思考

1. **阈值该怎么定**：现在只是"看分数"，更进一步是给运营一个「合格线」提示——比如 <0.5 的分片标红并且文案提示"召回质量偏低，建议补充文档内容"。但 COSINE 分数依赖 embedding 模型，**换模型后阈值要重新标定**，所以先收集一批真实分布再定。
2. **为什么需要"按 doc_id 过滤"的测试**：运营可能想验证「这篇刚传的文档能不能被召回」。可以给接口加可选参数 `doc_id`，走 Qdrant 的 `filter`——想想这和「测试该文档是否该删」的验证手段是不是同一个能力。
3. **分片质量的可视化**：现在的卡片已经是「原文 + 分数」，如果再显示分片序号（chunk index，需要写进 metadata），就能看出"答案被切到边界上了"——这是分片参数 `chunk_size=200/overlap=30` 调优的直接依据。这需要改 [kb_index_worker.py](../../python_agent/kb_index_worker.py) 的 metadata。
4. **为什么不做成"聊天式测试"**：让模型基于检索结果回答，更接近真实体验。但那就又要消耗 token、又会写消息/命中记录，且无法区分检索问题还是模型问题——**诊断工具和体验工具应该分开**，这是产品设计上的取舍。
5. **权限粒度**：这个接口能泄露知识库原文内容（虽然登录用户本来就能预览文档）。如果将来有"只能查看列表不能看内容"的角色，这里的 `KnowledgeView` 就要重新拆分。

### 需求 8：知识库文档版本管理（P3-2 之一）

**需求**：同一文档重复上传时不再新增记录，而是生成新版本：保留最近 3 个历史版本（可回滚），检索永远只用最新版本。

**涉及技术**：Postgres 表设计、Qdrant 替换语义、Redis 队列

**提示**：
- 表设计参考 prompt 版本管理：`prompts` + `prompt_versions` 两张表（`db_ops.py` 里 `load_active_prompt` 的用法），照这个模式设计 `kb_document_versions`
- 「同一文档」怎么判定？简单方案：按 `tenant_id + title` 相同视为同一文档；或上传时允许传 `doc_id` 表示更新
- 版本切换时 Qdrant 向量怎么替换？好消息：worker 已经是幂等设计（先删 doc_id 的旧 points 再写入），所以「回滚 = 把旧版本文件路径换回来 + 触发 reindex」，核心逻辑能复用
- 历史版本文件落盘命名建议 `{doc_id}_v{n}{ext}`，注意 file_url 生成逻辑 [routers_kb.py](../../python_agent/routers_kb.py) `kb_file_url` 目前不含版本号
- 范围控制：先做「上传新版本 + 回滚」，列表展示版本数即可，不做 diff

**验收**：同标题文档传 3 次 → 版本列表有 3 条 → 回滚到 v1 → 检索返回 v1 内容 → 超过 3 个版本最旧的被清理（DB 行 + 文件 + 无残留）。

### 需求 10：检索结果缓存搬到 Redis（多实例一致性）

**需求**：把 [cache.py](../../python_agent/cache.py) 的进程内字典缓存换成 Redis，key 带租户前缀，支持需求 4 的租户级失效在多实例间生效。

**涉及技术**：Redis（redis-py asyncio）、序列化、缓存雪崩防护

**提示**：
- 现状：`_kb_cache` 是模块级 dict，多实例各存一份。换成 Redis 后天然共享
- 注意 `search_kb` 是 async 的，用 `redis.asyncio` 客户端（`app.state.redis_client` 现成可用）
- key 设计：`cs:kb:cache:{tenant_id}:{md5(query)}`，TTL 用 `SETEX`
- 租户级失效：`SCAN cs:kb:cache:{tenant_id}:*` + 批量 DEL（想想生产上 SCAN vs KEYS 的区别）
- 进阶挑战：热点 key 失效瞬间大量请求同时穿透到 Qdrant（缓存击穿）——了解「单飞/singleflight」模式，Python 里可以用 `asyncio.Lock` 按 key 粒度加锁

**验收**：`docker compose exec redis redis-cli KEYS 'cs:kb:cache:*'` 能看到缓存项；删除文档后对应租户的 key 立即消失；TTL 到期自动过期。
