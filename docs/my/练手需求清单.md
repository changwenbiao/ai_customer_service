### 需求 3：知识库命中记录补上真实相似度分数（详解版）

**需求**：现在 `kb_hits.score` 大量是 0，因为 `similarity` 检索返回的 Document 没带 score。改成用带分数的检索，把真实相似度存进去。

**涉及技术**：LangChain Retriever/VectorStore API、Qdrant COSINE 相似度、PostgreSQL

#### 背景：这个分数有什么用

`kb_hits` 表是知识库闭环的核心数据——运营靠它回答两个问题：

1. **哪些文档经常被命中？**（列表页 hit_count 排序，已在用）
2. **检索质量怎么样？**（score 分布：命中的分数都很低 → 说明知识库内容跟用户问题对不上，需要补文档；分数高但没解决问题 → 说明文档内容写得不好）

现在第 2 个问题是瞎的，因为 score 全是 0：

```sql
SELECT query, doc_title, score FROM kb_hits ORDER BY id DESC LIMIT 10;
-- 现状：score 列全是 0.0
```

#### 根因分析

现状代码在 [tools.py](../../python_agent/tools.py)：

```python
# search_kb 里（约 L77）
docs = await retriever.ainvoke(query)        # ← 问题在这：retriever 只返回 Document，不带分数

# _record_kb_hits 里（约 L31-36）
rows = [
    (tid, thread_id, d.metadata.get("doc_id", ""), d.metadata.get("title", ""), query,
     float(getattr(d, "metadata", {}).get("score", 0) or 0))   # ← metadata 里根本没有 score 键
    for d in docs
]
```

链条是这样的：

- `retriever = store.as_retriever(search_type="similarity", search_kwargs={"k": 3})`（[agent_factory.py](../../python_agent/agent_factory.py) `get_tenant_retriever`）
- Retriever 的 `ainvoke(query)` 返回 `list[Document]`，**API 设计上就不含分数**（Retriever 的职责是"取回相关文档"，分数被丢弃了）
- 所以 `d.metadata.get("score", 0)` 永远拿到默认值 0

#### 预备知识：tenant_stores 与 tenant_retrievers 是什么关系

它们都是 `app.state` 上的**进程内字典缓存**，键都是 `tenant_id`，但装的东西不同：

```
app.state.tenant_stores     {tenant_id: QdrantVectorStore}   ← 向量库连接本体
app.state.tenant_retrievers {tenant_id: VectorStoreRetriever} ← store 的"预设参数外壳"
```

用一张图看关系和初始化过程：

```
租户第一次聊天
  │
  ▼ get_tenant_agent(app, tenant_id)          [agent_factory.py L429]
  │
  ├─► ensure_tenant_vector(app, tenant_id)    [L69]
  │     │  检查 tenant_stores 有没有 → 有就直接返回（缓存）
  │     │  没有则：
  │     │    1. 拿租户 embedding 模型（BYOK 配置）
  │     │    2. Qdrant 里没有 kb_{tenant} 集合就创建（COSINE，维度自动探测）
  │     │    3. 构建 QdrantVectorStore(client, collection, embedding)
  │     │    4. 存进 tenant_stores[tenant_id] ✅
  │     │  任何一步失败 → 返回 None + 60 秒冷却（对话降级为纯 LLM）
  │     ▼
  ├─► get_tenant_retriever(app, tenant_id)    [L111]
  │     │  检查 tenant_retrievers 有没有 → 有就直接返回（缓存）
  │     │  没有则从 tenant_stores 取 store，包一层：
  │     │    retriever = store.as_retriever(search_type="similarity",
  │     │                                 search_kwargs={"k": 3})
  │     │  存进 tenant_retrievers[tenant_id] ✅
  │     ▼
  └─► create_agent(...) 建租户 Agent，存进 tenant_agents[tenant_id]
```

一句话：**store 是"连接"，retriever 是"带着 k=3 参数的连接快捷方式"**。`retriever.ainvoke(query)` 等价于 `store.asimilarity_search(query, k=3)`，retriever 没有额外能力。

**失效与重建**（这是本需求要改代码时必须知道的）：

- 知识库任何变更（删除/重索引/批量/手动入队）后，代码都会执行 `tenant_retrievers.pop(tenant_id, None)`——因为集合内容变了，想让下次检索用新的
- 重建是**懒触发**的：下一次该租户聊天时，`get_tenant_agent` 会兜底检查 `tenant_id not in tenant_retrievers` 就重建（这个兜底是刚修过的 Bug，之前 pop 之后永远不重建，检索会卡死在「知识库暂未就绪」）
- `tenant_stores` 只在进程重启或模型配置变更时清——删文档**不需要**重建 store（连接还是同一个，只是里面的向量少了）

**对本需求的意义**：因为要拿分数，我们要**绕过 retriever 直接调 store**。所以改造后 `tenant_retrievers` 这条线对 search_kb 就没用了（`ensure_tenant_vector` 建的 store 才是我们要的）。

#### 改造方案

**第 1 步：改用带分数的 API**

`QdrantVectorStore` 本体有 `asimilarity_search_with_score(query, k=...)`，返回 `list[(Document, score)]`。不再走 retriever，直接拿 store：

```python
# tools.py search_kb 中，把原来的：
#   retriever = _app.state.tenant_retrievers.get(tid)
#   if retriever is None: return "知识库暂未就绪，请稍后再试。"
#   docs = await retriever.ainvoke(query)
# 改为：

from config import RETRIEVER_TOP_K

store = _app.state.tenant_stores.get(tid)     # 注意：换 tenant_stores，不是 tenant_retrievers
if store is None:
    return "知识库暂未就绪，请稍后再试。"
try:
    docs_with_scores = await store.asimilarity_search_with_score(query, k=RETRIEVER_TOP_K)
except Exception as e:
    _logger.warning(f"[KB Degrade] tenant={tid} 检索失败，降级为纯LLM: {str(e)[:150]}")
    return "知识库暂未就绪，请稍后再试。"
docs = [doc for doc, _score in docs_with_scores]   # 拼装回答文本用
```

> 顺带思考：改了之后 `tenant_retrievers` 缓存就没用了。保留它还是删掉？各有什么影响？（提示：retriever 是 store 的轻量包装，删了无功能损失，但要确认没有别处调用 `get_tenant_retriever`——grep 一下）

**第 2 步：搞清楚 score 的语义（重要，别想当然）**

项目 Qdrant 集合用的是 `Distance.COSINE`（`ensure_tenant_vector` 里创建）。Qdrant 的 COSINE 返回的是**余弦相似度**：**越大越相似**，范围大致 [-1, 1]，常见命中在 0.5~0.9。

动手前先用 API 验证一下真实分布，别猜：

```bash
# 先正常聊几句产生向量，然后直接查 Qdrant 看分数
curl -s -X POST localhost:6333/collections/kb_t_demo/points/scroll \
  -H 'Content-Type: application/json' \
  -d '{"limit": 3, "with_payload": true, "with_vector": true}' 
# 拿到一个向量后，用它 search 看 score 值长什么样（也可做完第 1 步后直接看 kb_hits 数据）
```

**第 3 步：改造 `_record_kb_hits` 接收分数**

函数签名从收 `docs` 改为收 `docs_with_scores`：

```python
async def _record_kb_hits(tid: str, thread_id: str, query: str, docs_with_scores: list) -> None:
    try:
        if docs_with_scores:
            rows = [
                (tid, thread_id,
                 d.metadata.get("doc_id", ""), d.metadata.get("title", ""), query,
                 float(score))                      # ← 真实的相似度
                for d, score in docs_with_scores
            ]
        else:
            rows = [(tid, thread_id, "", "", query, 0.0)]
        # ... executemany 不变
```

`kb_hits.score` 字段是 `REAL`（init.sql 已定义），不用改表。

**第 4 步：保持原有降级行为不变（检查清单）**

- [ ] store 为 None → 返回「知识库暂未就绪，请稍后再试。」
- [ ] 检索异常 → warning 日志 + 同样的提示语，**不抛穿对话**
- [ ] 无结果 → 「未找到相关信息，建议转接人工客服。」+ 落一条空 doc_id 的未命中记录
- [ ] 缓存读写逻辑（`_kb_cache_get/_set`）不变
- [ ] 返回给模型的文本格式不变（`"\n".join(f"- {doc.page_content}")`）

## L2 进阶级（跨服务改动，需要理解链路）

### 需求 4：知识库变更后立刻失效检索缓存（修一致性缺陷）（详解版）

#### 背景

`search_kb` 的检索结果有进程内缓存（[cache.py](../../python_agent/cache.py)），同一个租户问同一个问题，TTL 内直接返回缓存答案。但**知识库内容变了，缓存不会变**：

- 删掉一篇文档 → 最长 TTL 时间内，用户还能问到这篇文档里的内容（已删除信息泄露）
- 重索引一篇修改过的文档 → TTL 内用户拿到的还是旧版答案
- 管理端「命中明细/最近命中」统计也会失真（缓存命中不走检索、不写 `kb_hits`，这是另一个已知行为）

TTL 越长性能越好、一致性越差；TTL 越短则相反（你之前把 TTL 改成 10s 调试，就是把这个矛盾缩小到了 10 秒）。**正确做法不是靠短 TTL，而是变更时主动失效缓存**——性能和一致性兼得。

#### 根因分析

现状缓存模块（[cache.py](../../python_agent/cache.py)，全文仅 52 行）：

```python
# key: "tenant_id:query_hash", value: (expire_time, result)
_kb_cache = {}

def _kb_cache_key(tenant_id: str, query: str) -> str:
    q_hash = hashlib.md5(query.strip().lower().encode('utf-8')).hexdigest()
    return f"{tenant_id}:{q_hash}"          # ← key 自带租户前缀，这是能按租户清理的关键

def clear_kb_cache():
    """清空全部缓存（模型/向量配置变更时调用）"""
    _kb_cache.clear()                        # ← 只有"全清"，没有"按租户清"
```

问题有两个：

1. **没有按租户清理的函数**——`clear_kb_cache()` 只能全清，而 KB 变更只影响一个租户，全清会误伤其他租户的热缓存
2. **KB 变更的代码路径根本没调用任何清理**——[routers_kb.py](../../python_agent/routers_kb.py) 的删除/重索引/批量接口只做了 Qdrant 删向量、DB 删记录、（改造前）pop retriever，从未碰 `_kb_cache`

#### 预备知识：什么时刻算"知识库变了"

这是本需求最容易做错的地方——**不是每个接口调用时都该清缓存**，要看向量内容什么时候真正变化：

| 操作 | 向量何时变化 | 该在何处清缓存 |
|---|---|---|
| 上传文档（status=0 待索引） | 还没建向量 | ❌ 不用清 |
| 删除文档 / 批量删除 | 接口里**立即**删了 Qdrant 向量 | ✅ 接口里立即清 |
| 重索引 / 批量重索引 | 接口里先删旧向量，worker **异步**写新向量 | ✅ 接口里清（删旧）+ worker 完成时清（写新）|
| 手动入队 `/kb/index` | 入队时不变，worker 完成才变 | ✅ worker 完成时清 |
| worker 索引成功（status=1） | 新向量此刻生效 | ✅ [kb_index_worker.py](../../python_agent/kb_index_worker.py) `_index_one` 成功分支 |

关键点：**worker 和 FastAPI 在同一个进程**（`main.py` lifespan 里 `asyncio.create_task(index_worker_loop(...))` 启动），所以 worker 可以直接调 `cache.py` 的函数操作同一个 `_kb_cache` 字典，不需要跨进程通信。

#### 改造方案

**第 1 步：cache.py 加按租户清理函数**

```python
def clear_kb_cache(tenant_id: str | None = None):
    """清空知识库检索结果缓存。
    tenant_id 为 None → 全清（模型/向量配置变更时用）；
    指定 tenant_id → 只清该租户（KB 文档变更时用，不误伤其他租户）。
    key 格式为 "tenant_id:md5(query)"，按前缀匹配。
    """
    if tenant_id is None:
        n = len(_kb_cache)
        _kb_cache.clear()
        return n
    prefix = f"{tenant_id}:"
    keys = [k for k in _kb_cache if k.startswith(prefix)]
    for k in keys:
        del _kb_cache[k]
    return len(keys)
```

**第 2 步：在变更点调用**（对照上面的时机表）

- `routers_kb.py` `kb_delete`：删完向量/记录后调 `clear_kb_cache(tenant_id)`
- `routers_kb.py` `kb_reindex`：删完旧向量后调（别等 worker，中间窗口期旧答案必须失效）
- `routers_kb.py` `kb_batch`：`delete` 和 `reindex` 两个分支都要调
- `kb_index_worker.py` `_index_one`：UPDATE status=1 成功后调（`clear_kb_cache` 是同步函数，直接调，别用 await）

调用处加一行日志 `logger.info("KB cache invalidated tenant=%s n=%d", tenant_id, n)`，方便验收时观察。

**第 3 步：检查遗漏**

`grep -rn "clear_kb_cache" python_agent/`，确认所有「会改向量内容」的路径都覆盖了；再反向确认「只改元数据不改向量」的操作（比如单纯改分类 `category`）**没有**误清——改分类不影响检索内容，清了是浪费。

#### 验收

```bash
docker compose up -d --build agent
```

1. 上传一篇文档（内容包含一个独特事实，如"本平台的吉祥物是蓝色大象"）→ 索引 → 聊天问"吉祥物是什么"，得到答案 A
2. 删除该文档
3. **立刻**再问同样的问题 → 答案不能再是 A（缓存命中会直接返回旧答案 A，失效成功则会走真实检索返回"未找到相关信息"）
4. 重索引场景同理：改文档内容 → 重索引 → 等 status=1 → 再问，必须是新答案
5. 看日志里 `KB cache invalidated` 的触发次数和时机是否符合预期

#### 扩展思考

1. **多实例部署怎么办**：本项目只跑一个 agent 容器，进程内清理够用。如果将来水平扩容，单实例清缓存其他实例不知道——项目已有现成的 Redis 广播机制（[redis_pubsub.py](../../python_agent/redis_pubsub.py) 的 `invalidate_listener`，现在用于模型配置失效广播），模仿它加一种 `kb_cache` 消息类型即可，这也是需求 10 的前置。
2. **重索引窗口期的行为**：reindex 接口清缓存后、worker 写完新向量前，用户提问会得到"未找到相关信息"。这比返回旧答案好（一致性优先），但你能不能接受？能不能做得更好（比如保留旧向量直到新向量写完再切换）？
3. **清缓存的粒度**：现在是"文档一变就清整个租户"。如果租户有 1000 篇文档只改了 1 篇，全部查询缓存失效会不会太狠？更细粒度需要知道"哪些 query 命中过这篇文档"——`kb_hits` 表里有 query 和 doc_id 的对应关系，理论上能反推，值得吗？

### 需求 5：工单 SLA——人工超时未响应自动提醒（P3-3）

**需求**：工单处于 `pending`（待接管）超过 10 分钟没有客服接管时，给用户发一条系统消息「客服繁忙，正在加急处理，请稍候」，并（可选）在管理端工单列表置顶标红。

**涉及技术**：Go 定时任务、MySQL 查询、WebSocket 推送

**提示**：
- 工单表结构：`tickets`（status: pending/handling/closed），看 `go_service/internal/service/ticket_service.go` 和 `deploy/init/mysql/` 的建表 SQL
- 定时任务参考：Go 里可以用 `time.Ticker` 起一个 goroutine，在 `main.go` 启动时注册；Python 侧有类似例子（`session_cleanup_loop`）
- 推送消息给用户走 WS hub：[ws.go](../../go_service/internal/handler/ws.go) 里 `users map[string]*Client` 的结构和发消息方式（回忆：onChunk 怎么推的）
- 注意幂等：提醒过一次要记录（比如 tickets 加字段或 Redis 标记），否则每 10 分钟刷一条
- 配置项做成 env：`TICKET_SLA_MINUTES`

### 需求 8：知识库文档版本管理（P3-2 之一）

**需求**：同一文档重复上传时不再新增记录，而是生成新版本：保留最近 3 个历史版本（可回滚），检索永远只用最新版本。

**涉及技术**：Postgres 表设计、Qdrant 替换语义、Redis 队列

**提示**：
- 表设计参考 prompt 版本管理：`prompts` + `prompt_versions` 两张表（`db_ops.py` 里 `load_active_prompt` 的用法），照这个模式设计 `kb_document_versions`
- 「同一文档」怎么判定？简单方案：按 `tenant_id + title` 相同视为同一文档；或上传时允许传 `doc_id` 表示更新
- 版本切换时 Qdrant 向量怎么替换？好消息：worker 已经是幂等设计（先删 doc_id 的旧 points 再写入），所以「回滚 = 把旧版本文件路径换回来 + 触发 reindex」，核心逻辑能复用
- 历史版本文件落盘命名建议 `{doc_id}_v{n}{ext}`，注意 file_url 生成逻辑 [routers_kb.py](../../python_agent/routers_kb.py) `kb_file_url` 目前不含版本号
- 范围控制：先做「上传新版本 + 回滚」，列表展示版本数即可，不做 diff

**验收**：同标题文档传 3 次 → 版本列表有 3 条 → 回滚到 v1 → 检索返回 v1 内容 → 超过 3 个版本最旧的被清理（DB 行 + 文件 + 无残留）。

### 需求 10：检索结果缓存搬到 Redis（多实例一致性）

**需求**：把 [cache.py](../../python_agent/cache.py) 的进程内字典缓存换成 Redis，key 带租户前缀，支持需求 4 的租户级失效在多实例间生效。

**涉及技术**：Redis（redis-py asyncio）、序列化、缓存雪崩防护

**提示**：
- 现状：`_kb_cache` 是模块级 dict，多实例各存一份。换成 Redis 后天然共享
- 注意 `search_kb` 是 async 的，用 `redis.asyncio` 客户端（`app.state.redis_client` 现成可用）
- key 设计：`cs:kb:cache:{tenant_id}:{md5(query)}`，TTL 用 `SETEX`
- 租户级失效：`SCAN cs:kb:cache:{tenant_id}:*` + 批量 DEL（想想生产上 SCAN vs KEYS 的区别）
- 进阶挑战：热点 key 失效瞬间大量请求同时穿透到 Qdrant（缓存击穿）——了解「单飞/singleflight」模式，Python 里可以用 `asyncio.Lock` 按 key 粒度加锁

**验收**：`docker compose exec redis redis-cli KEYS 'cs:kb:cache:*'` 能看到缓存项；删除文档后对应租户的 key 立即消失；TTL 到期自动过期。
