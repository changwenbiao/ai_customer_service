## L1 入门级（熟悉代码结构，改动小）

### 需求 1：Makefile 一键入口（P2-4，规划里未做的）

**需求**：在项目根目录创建 `Makefile`，提供 `make build / test / up / logs / healthcheck` 五个命令，内部调用现有 scripts。

**涉及技术**：Makefile 语法、Docker Compose、Shell 脚本

**提示**：
- 先看 `scripts/` 目录下已有脚本：`run_p0_tests.sh`、`run_healthcheck.sh`、`build_admin_app.sh`
- 全量启动命令是 `docker compose up -d --build`；调试模式是 `docker compose -f docker-compose.yaml -f docker-compose.debug.yaml up -d --build`（见 [远程调试指南.md](./远程调试指南.md)）
- Makefile 的 target 里命令必须以 Tab 开头；加 `.PHONY` 防止与同名文件冲突

**验收**：`make test` 能跑通 Go+Python 测试；`make healthcheck` 输出 14 项断言结果。

### 需求 2：批量删除补删原文件（修一个真实的 Bug）

**需求**：现在 `POST /agent/kb/batch` 的 `delete` 动作只删了 DB 和 Qdrant，**共享卷里的原文件会残留**（单条删除接口会删文件，批量不会）。补上文件清理。

**涉及技术**：Python、FastAPI、异步循环

**提示**：
- 代码在 [routers_kb.py](../../python_agent/routers_kb.py) 的 `kb_batch` 函数（约 L493-509），`action == "delete"` 分支
- 单条删除怎么删文件的？看同文件 `kb_delete`（约 L299-330）里 `delete_kb_file` 的用法
- 批量分支目前没查 `file_name`，你需要先 `SELECT doc_id, file_name ...` 拿到文件名列表
- 删除文件用现成的 `delete_kb_file(tenant_id, doc_id, file_name)`，循环调用即可
- 想想：删文件失败要不要让接口报错？（参考单条删除的「尽力而为」策略）

**验收**：批量删除 2 个文档后，`docker compose exec agent ls /app/data/kb_files/{tenant}` 里对应文件消失。

### 需求 3：知识库命中记录补上真实相似度分数

**需求**：现在 `kb_hits.score` 大量是 0，因为 `similarity` 检索返回的 Document 没带 score。改成用带分数的检索，把真实相似度存进去。

**涉及技术**：LangChain Retriever API、Qdrant

**提示**：
- 现状代码在 [tools.py](../../python_agent/tools.py) `search_kb` 和 `_record_kb_hits`
- LangChain 的 VectorStore 有 `similarity_search_with_score(query, k=...)` 方法，返回 `(Document, score)` 列表
- 但 `search_kb` 现在用的是 retriever（`retriever.ainvoke`）。你可以改为直接用 `_app.state.tenant_stores.get(tid)` 拿 store 调 `asimilarity_search_with_score`
- 注意：COSINE 距离下 score 的含义（越小越相似还是越大越相似？查 langchain_qdrant 文档验证）
- 保持原有降级逻辑（retriever 为 None、异常时的提示语）不变

**验收**：聊几句后 `SELECT query, doc_title, score FROM kb_hits ORDER BY id DESC LIMIT 5;` 能看到非 0 分数。

## L2 进阶级（跨服务改动，需要理解链路）

### 需求 4：知识库变更后立刻失效检索缓存（修一致性缺陷）

**需求**：`cache.py` 的检索结果缓存 TTL 300 秒，文档删除/重索引后最长 5 分钟还会返回旧答案。要求知识库变更后**该租户的缓存立即失效**。

**涉及技术**：Python 字典缓存、缓存失效策略、（可选）Redis 广播

**提示**：
- 缓存实现在 [cache.py](../../python_agent/cache.py)，key 是 `tenant_id:md5(query)`
- 在 [routers_kb.py](../../python_agent/routers_kb.py) 的删除/重索引/批量接口里，已经有 `tenant_retrievers.pop(tenant_id, None)` 的失效动作——照着这个模式，在 cache.py 里加一个 `_kb_cache_invalidate_tenant(tenant_id)`，按 key 前缀清理
- 进阶挑战：如果 agent 是多实例部署，单实例清缓存不够——项目里已有 Redis 广播机制，看 [redis_pubsub.py](../../python_agent/redis_pubsub.py) 怎么广播模型配置失效的，模仿着加一种消息类型

**验收**：上传文档 → 索引 → 问出问题 A 得到答案 → 删除该文档 → 再问问题 A，回答不再是缓存里的旧内容。

### 需求 5：工单 SLA——人工超时未响应自动提醒（P3-3）

**需求**：工单处于 `pending`（待接管）超过 10 分钟没有客服接管时，给用户发一条系统消息「客服繁忙，正在加急处理，请稍候」，并（可选）在管理端工单列表置顶标红。

**涉及技术**：Go 定时任务、MySQL 查询、WebSocket 推送

**提示**：
- 工单表结构：`tickets`（status: pending/handling/closed），看 `go_service/internal/service/ticket_service.go` 和 `deploy/init/mysql/` 的建表 SQL
- 定时任务参考：Go 里可以用 `time.Ticker` 起一个 goroutine，在 `main.go` 启动时注册；Python 侧有类似例子（`session_cleanup_loop`）
- 推送消息给用户走 WS hub：[ws.go](../../go_service/internal/handler/ws.go) 里 `users map[string]*Client` 的结构和发消息方式（回忆：onChunk 怎么推的）
- 注意幂等：提醒过一次要记录（比如 tickets 加字段或 Redis 标记），否则每 10 分钟刷一条
- 配置项做成 env：`TICKET_SLA_MINUTES`

**验收**：创建工单无人接管，10 分钟后用户端收到系统消息；接管后不再提醒。

### 需求 6：业务指标进 Prometheus（P3-4 收尾）

**需求**：在现有 metrics 框架上新增 3 个业务指标：
1. `cs_messages_total{tenant_id, role}` 消息量（用户/AI/人工分开计数）
2. `cs_tickets_total{tenant_id, action}` 工单量（created/closed）
3. `cs_transfer_to_human_total{tenant_id}` 转人工次数（配合工单量可算转人工率）

**涉及技术**：Prometheus client_golang、Go 中间件/埋点、Grafana

**提示**：
- 现有指标定义在 [metrics.go](../../go_service/internal/middleware/metrics.go)，照着 `agentCallsTotal` 的写法加 CounterVec
- 埋点位置：消息落库在 `ws.go` 的 onEnd 回调（回忆 onEnd 干什么）——**注意别在消息处理热路径上埋高基数 label**（tenant_id 可以，thread_id 不行，想想为什么）
- 转人工的埋点在 Go 处理 interrupt 的回调里（onInterrupt / resume 接口附近）
- Grafana 面板 JSON 在 `deploy/observability/`（该目录被 gitignore，本地应该有），加一个 panel 展示转人工率：`rate(cs_transfer_to_human_total[1h]) / rate(cs_messages_total{role="user"}[1h])`

**验收**：`curl localhost:8080/metrics | grep cs_messages` 有数据；聊几轮 + 转一次人工后数值增长；Grafana 能看到曲线。

### 需求 8：知识库文档版本管理（P3-2 之一）

**需求**：同一文档重复上传时不再新增记录，而是生成新版本：保留最近 3 个历史版本（可回滚），检索永远只用最新版本。

**涉及技术**：Postgres 表设计、Qdrant 替换语义、Redis 队列

**提示**：
- 表设计参考 prompt 版本管理：`prompts` + `prompt_versions` 两张表（`db_ops.py` 里 `load_active_prompt` 的用法），照这个模式设计 `kb_document_versions`
- 「同一文档」怎么判定？简单方案：按 `tenant_id + title` 相同视为同一文档；或上传时允许传 `doc_id` 表示更新
- 版本切换时 Qdrant 向量怎么替换？好消息：worker 已经是幂等设计（先删 doc_id 的旧 points 再写入），所以「回滚 = 把旧版本文件路径换回来 + 触发 reindex」，核心逻辑能复用
- 历史版本文件落盘命名建议 `{doc_id}_v{n}{ext}`，注意 file_url 生成逻辑 [routers_kb.py](../../python_agent/routers_kb.py) `kb_file_url` 目前不含版本号
- 范围控制：先做「上传新版本 + 回滚」，列表展示版本数即可，不做 diff

**验收**：同标题文档传 3 次 → 版本列表有 3 条 → 回滚到 v1 → 检索返回 v1 内容 → 超过 3 个版本最旧的被清理（DB 行 + 文件 + 无残留）。

### 需求 10：检索结果缓存搬到 Redis（多实例一致性）

**需求**：把 [cache.py](../../python_agent/cache.py) 的进程内字典缓存换成 Redis，key 带租户前缀，支持需求 4 的租户级失效在多实例间生效。

**涉及技术**：Redis（redis-py asyncio）、序列化、缓存雪崩防护

**提示**：
- 现状：`_kb_cache` 是模块级 dict，多实例各存一份。换成 Redis 后天然共享
- 注意 `search_kb` 是 async 的，用 `redis.asyncio` 客户端（`app.state.redis_client` 现成可用）
- key 设计：`cs:kb:cache:{tenant_id}:{md5(query)}`，TTL 用 `SETEX`
- 租户级失效：`SCAN cs:kb:cache:{tenant_id}:*` + 批量 DEL（想想生产上 SCAN vs KEYS 的区别）
- 进阶挑战：热点 key 失效瞬间大量请求同时穿透到 Qdrant（缓存击穿）——了解「单飞/singleflight」模式，Python 里可以用 `asyncio.Lock` 按 key 粒度加锁

**验收**：`docker compose exec redis redis-cli KEYS 'cs:kb:cache:*'` 能看到缓存项；删除文档后对应租户的 key 立即消失；TTL 到期自动过期。
