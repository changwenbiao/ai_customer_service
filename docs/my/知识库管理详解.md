# 知识库管理详解（上传 → 索引 → 检索 → 管理 → 运维）

> 本文覆盖 `ai_customer_service` 知识库（RAG）的完整链路：数据落在哪、状态怎么流转、索引怎么执行、对话里怎么被检索、后台怎么管理、权限/配额/缓存/降级怎么处理、出问题怎么排查。
>
> 关键代码位置（相对项目根目录）：
> - `../../python_agent/routers_kb.py`：知识库后台管理接口（上传/列表/删除/分类/重索引/批量/平台设置）
> - `../../python_agent/kb_index_worker.py`：异步索引 worker（消费 Redis 队列，分片 → embedding → Qdrant）
> - `../../python_agent/kb_parser.py`：文件文本解析（txt/md/csv/pdf/docx/xlsx）
> - `../../python_agent/agent_factory.py`：租户向量库/Retriever 构建、BYOK 模型配置
> - `../../python_agent/tools.py`：`search_kb` 工具（对话检索入口）与命中落库
> - `../../python_agent/cache.py`：检索结果进程内缓存（TTL 300s）
> - `../../python_agent/db_ops.py`：集合命名、配额校验、平台设置读写
> - `../../python_agent/main.py`：启动时建表校验、worker 拉起、崩溃兜底重入队
> - `../../go_service/internal/router/router.go`：知识库路由与权限
> - `../../go_service/internal/handler/proxy.go`：`ProxyKbUpload` multipart 重组转发
> - `../../deploy/init/postgres/init.sql`：`kb_documents` / `kb_hits` / `platform_settings` 表结构
> - `../../docker-compose.yaml`：理论知识库原文件共享卷 `cs_kb_files`

一句话总结：**Postgres 存元数据与命中记录，共享卷存原文件（唯一数据源），Redis 做异步索引队列，Qdrant 存向量，nginx 静态提供原文件下载/预览。**

## 2. 依赖组件与职责

| 组件 | 用途 | 关键点 |
|---|---|---|
| PostgreSQL | `kb_documents`（文档元数据/状态/命中统计来源）、`kb_hits`（检索命中明细）、`platform_settings`（平台级 KV 配置） | 表结构只在 `init.sql` 维护，Agent 启动仅校验存在性 |
| Redis | 索引队列 `cs:kb:index:queue`（List），同时承载模型配置缓存失效广播 | Agent **强依赖** Redis：启动时 `ping()` 失败直接启动失败 |
| Qdrant | 向量库，**每个租户一个 collection**：`kb_{tenant_id}`，无租户为 `kb_default` | 距离度量 `COSINE`，维度由 embedding 探测 |
| 共享卷 `cs_kb_files` | 原文件唯一数据源 | Agent 挂 `/app/data/kb_files`，nginx 挂 `/usr/share/nginx/html/kb_files` |
| nginx | 静态服务 `/kb_files/` | 前端下载/预览直接走 `file_url` |
| Embedding 模型 | BYOK（平台/租户模型配置，DB 单一数据源） | 不可用时知识库降级（索引失败/检索不可用），不影响对话本身 |

## 3. 数据模型

### 3.1 `kb_documents`（文档元数据）

定义见 `../../deploy/init/postgres/init.sql`（第 63-80 行）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGSERIAL PK | 自增主键 |
| `doc_id` | VARCHAR(64) UNIQUE | 业务文档 ID，`uuid4().hex`，也是落盘文件名 |
| `tenant_id` | VARCHAR(64) | 租户隔离键，来自请求头 `X-Tenant-Id` |
| `title` | VARCHAR(255) | 展示标题，缺省为文件名 |
| `chunk_count` | INT | 索引成功后的分片数（失败/未索引为 0） |
| `created_at` | TIMESTAMPTZ | 创建时间（列表默认排序依据） |
| `file_name` | VARCHAR(255) | 原始文件名（`text.txt` 表示粘贴文本） |
| `file_size` | INT | 字节数，用于容量配额统计 |
| `category` | VARCHAR(64) | 分类，默认 `默认` |
| `status` | SMALLINT | 索引状态，默认 1（见下表） |
| `error_msg` | TEXT | 失败原因（截断 500 字符） |
| `file_url` | VARCHAR(512) | `/kb_files/{tenant}/{doc_id}{ext}` |
| `updated_at` | TIMESTAMPTZ | 最近更新时间 |

索引：`idx_kb_tenant(tenant_id)`、`idx_kb_category(category)`、`idx_kb_status(status)`。

> 注意：**`content` 列已废弃**。历史表曾有该列，现在全文以共享卷原文件为唯一数据源，列表接口也不拉取大字段。

### 3.2 状态机（`status`）

| 值 | 含义 | 谁会写入 |
|---|---|---|
| `0` | 待索引（含上传后待手动索引、失败后重新入队、重索引） | 上传 INSERT、`/kb/index`、`/reindex` |
| `1` | 已索引成功 | worker 完成后 |
| `2` | 索引失败 | worker `_mark_failed`、Redis 队列不可用 |
| `3` | 索引中 | worker 开始处理时 |

流转：

```
上传 ──INSERT──> 0(待索引)
                  │ 用户点「开始索引 / 重索引」→ /kb/index | /reindex
                  ▼
                 LPUSH 队列 ──worker BLPOP──> 3(索引中)
                                              ├─ 成功 → 1(已索引)，chunk_count 更新
                                              └─ 失败 → 2(失败)，error_msg 记录原因

进程崩溃：status=3 残留 ──Agent 启动 requeue_pending──> 重新入队 → 3 → 1/2
```

**重要设计**：`status=0` 是「待手动索引」的稳定态，启动兜底**不会**自动消费 status=0（见 `kb_index_worker.requeue_pending`，第 135-154 行）；只重新入队 status=3（上次处理中崩溃）。

### 3.3 `kb_hits`（检索命中/未命中明细）

定义见 `init.sql` 第 84-96 行：

| 字段 | 说明 |
|---|---|
| `tenant_id` / `thread_id` | 租户与会话维度 |
| `doc_id` / `doc_title` | 命中文档；**空字符串表示这次检索未命中** |
| `query` | 用户检索词 |
| `score` | 相似度分数（取自文档 metadata `score`，缺失记 0） |
| `hit_at` | 命中时间 |

索引：`(tenant_id, doc_id)`、`(tenant_id, hit_at)`。

用途：知识库闭环统计——列表页的「命中次数 / 最近命中时间」、`order=hit_desc|hit_asc` 排序、未命中查询分析（找知识缺口）。

### 3.4 `platform_settings`（平台级 KV）

定义见 `init.sql` 第 105-110 行。当前使用的键：`kb_max_file_mb`（单文件上传上限，1-100 MB）。

读取顺序（`routers_kb._kb_max_file_mb`，第 37-49 行）：
1. `platform_settings.kb_max_file_mb`
2. 环境变量 `KB_MAX_FILE_MB`
3. 常量 `DEFAULT_MAX_FILE_MB = 10`

### 3.5 存储布局

```
共享卷 cs_kb_files
├── {tenant_id}/
│   ├── {doc_id}.pdf
│   ├── {doc_id}.docx
│   └── {doc_id}.txt      ← 粘贴文本也统一落成 txt
Qdrant
└── kb_{tenant_id}
    └── points: { id: uuid, vector: [...], payload: {doc_id, title, source:"kb", tenant_id} }
Redis
└── List cs:kb:index:queue → {"doc_id": "...", "tenant_id": "..."}
```

## 4. 上传流程（`POST /agent/kb/upload`）

代码：`routers_kb.py` 第 119-210 行。Go 侧入口：`/api/biz/kb/upload`（`router.go` 第 178 行，权限 `KnowledgeAdd`），`ProxyKbUpload`（`proxy.go` 第 85-115 行）负责把 multipart 重新打包（`file` + `title` + `category`）转发，非文件请求按 JSON 透传。

### 4.1 两种入参

| 入参 | 处理 |
|---|---|
| `multipart/form-data` + `file` | 读原始字节 → 大小校验 → `extract_text` 解析 → 落盘原文件 |
| `application/json`（或 form 的 `content`） | 取 `title/content/category`，文本落盘为 `text.txt`（无文件时） |

字段：`title`（缺省用文件名）、`category`（默认 `默认`）、`content`（文本粘贴）。

### 4.2 处理步骤

1. **生成 `doc_id`**：`uuid.uuid4().hex`（唯一，且直接作为磁盘文件名）。
2. **大小限制**：`len(raw) > max_mb * 1024 * 1024` → 返回 400「文件超过大小限制（N MB）」。
3. **文本解析**：`kb_parser.extract_text(file_name, raw)`。
   - 支持扩展名 `SUPPORTED_EXTS = {".txt", ".md", ".csv", ".pdf", ".docx", ".xlsx"}`。
   - 不支持格式抛 `RuntimeError("暂不支持 .xxx 格式…")` → 返回 `code=400`。
   - 解析结果为空 → 400「文件无可提取文本」。
   - 解析库懒加载：缺 `pypdf` / `python-docx` / `openpyxl` 时给出明确依赖缺失提示。
   - PDF 扫描件（无文本层）→ `"PDF 无可提取文本（可能为扫描件/图片型 PDF，暂不支持 OCR）"`。
4. **原文件落盘**：`save_kb_file(tenant, doc_id, file_name, raw)` 写到 `/app/data/kb_files/{tenant}/{doc_id}{ext}`；失败 → 500。
5. **生成 `file_url`**：`kb_file_url()` → `/kb_files/{tenant}/{doc_id}{ext}`（无扩展名返回空串）。
6. **配额校验**：`check_kb_quota(conn, app, tenant_id)`：
   - `max_kb_docs > 0` 且 `count(*) >= max` → 429「文档数已达上限」；
   - `max_kb_size_mb > 0` 且 `SUM(file_size) >= max*MB` → 429「容量已达上限」；
   - 配额超限时**清理已落盘文件**再返回。
7. **写库**：`INSERT INTO kb_documents (..., status=0, file_url)`。
8. **返回**：`{doc_id, title, chunk_count:0, char_count, category, file_name, file_size, status:0, file_url, msg:"已上传，待手动索引"}`。

> **为什么上传不自动索引？**
> 1. 避免大文件上传即消耗 embedding 配额；
> 2. 便于统一批量控制索引进度（前端弹窗轮询）；
> 3. 让用户显式确认「开始索引」。

### 4.3 前端行为（`../../admin-app/src/views/Knowledge.vue`）

- 文件上传逐个调用 `/api/admin/kb/upload`，提示「已上传 N 个文件，待手动索引」。
- 「开始索引」按勾选或全部待索引/失败发起 `/api/admin/kb/index`。
- 进度弹窗每 **2 秒** 拉一次列表分页统计 `status` 分布，全部处理完自动关闭并刷新。
- 预览/下载直接 `window.open(file_url)`，不经过后端。
- 平台设置里可改 `kb_max_file_mb`（`PlatformSettings.vue`）。

## 5. 手动索引与重索引

### 5.1 `POST /agent/kb/index`（代码第 409-457 行）

请求体：
- `{"doc_ids": ["..."]}`：只处理指定文档（先做租户归属过滤，防越权）；
- `{}` 或空：处理该租户全部 `status IN (0,2)` 的文档。

执行：
1. 先把目标文档 `UPDATE status=0, error_msg=NULL`；
2. 逐个 `LPUSH` 队列；
3. 入队失败的文档立刻 `UPDATE status=2, error_msg='Redis 索引队列不可用'`；
4. 失效该租户 retriever 缓存（`tenant_retrievers.pop`）；
5. 返回 `{queued, failed, skipped}`。

### 5.2 `POST /agent/kb/documents/{doc_id}/reindex`（第 355-392 行）

与 `/kb/index` 的差异：
- **立即删除该文档在 Qdrant 的旧向量**（`Filter(doc_id == ...)`），避免重索引期间检索到旧内容；
- 置 `status=0`、清 `error_msg`，再入队；
- 入队失败返回 `code=500`「索引队列不可用，请稍后重试」。

### 5.3 `POST /agent/kb/batch`（第 460-527 行）

`{"action": "delete|reindex|category", "doc_ids": [...], "category": "..."}`：
- 先查归属，仅保留当前租户的 `doc_id`（其余计入 `skipped`）；
- `delete`：删 DB + 删 Qdrant（`MatchAny` 批量）+ 失效 retriever；
- `category`：批量改分类；
- `reindex`：复用单条 `kb_reindex`（因此也带 Qdrant 旧向量删除 + 入队）。

> 注意：批量 `delete` 不删除共享卷原文件（单条删除会删；批量删除只删 DB/Qdrant）。如需严格清理磁盘，可后续在批量分支补 `delete_kb_file`。

## 6. 异步索引 worker（`kb_index_worker.py`）

### 6.1 启动与并发

`main.py` 启动阶段：
1. `await kb_index_worker.requeue_pending(app)`：把 `status=3` 的残留重新入队（崩溃兜底）；
2. `KB_INDEX_WORKERS`（默认 `2`）个 `asyncio` 任务跑 `index_worker_loop(app, i)`；
3. 关闭时逐个 cancel。

### 6.2 消费循环（第 110-132 行）

```python
item = await r.blpop(KB_INDEX_QUEUE, timeout=5)   # 阻塞最多 5 秒
if item is None: continue
data = json.loads(item[1])
await _index_one(app, data["doc_id"], data["tenant_id"])
```

单条任务异常只记 warning，不影响后续消息；循环级异常 `sleep(2)` 后继续；`CancelledError` 直接抛出（优雅退出）。

### 6.3 `_index_one` 六步（第 25-95 行）

1. **查元数据**：`SELECT title, file_name FROM kb_documents WHERE doc_id AND tenant_id`；查不到 → skip。
2. **读原文**：`read_kb_file_text(tenant, doc_id, file_name)`（从共享卷重新解析，失败/空 → `status=2`「原文件缺失或无法解析，请重新上传」）。
3. **置 `status=3`**（索引中），清 `error_msg`。
4. **幂等删旧向量**：`delete(collection_name(tenant), Filter(doc_id == ...))` —— 重复消费/重索引不会产生重复 points。
5. **分片**：
   - `text = content[:MAX_TEXT_CHARS]`，`MAX_TEXT_CHARS = 1_000_000`（防 embedding 超时）；
   - `app.state.text_splitter.create_documents([text])`，切分参数来自 `config.py`：`chunk_size=200`、`chunk_overlap=30`；
   - 分片为空 → `status=2`「文档分片结果为空」。
6. **embedding + 写 Qdrant**：
   - `ensure_tenant_vector(app, tenant)`，返回 `None` → `status=2`「向量模型/向量库不可用，索引失败（请检查后台模型配置）」；
   - `vs.aadd_texts(texts, metadatas=[{doc_id, title, source:"kb", tenant_id}], ids=[uuid...])`；
   - 成功后 `UPDATE chunk_count=len(texts), status=1, error_msg=NULL`；
   - `tenant_retrievers.pop(tenant)` 让下一次对话重建 retriever；
   - 任一步异常 → `_mark_failed(status=2, err[:500])`。

### 6.4 失败信息（`_mark_failed`，第 98-107 行）

只写 `status=2` + `error_msg`（截断 500 字符），不重试。重试由用户手动「开始索引」（`status IN (0,2)` 会被重新入队）。

## 7. 向量化基础设施（`agent_factory.py`）

### 7.1 `ensure_tenant_vector(app, tenant_id)`（第 69-109 行）

- 已有 `app.state.tenant_stores[tenant]` → 直接返回；
- **失败冷却** `_VEC_FAIL_TTL = 60s`：近期失败过直接返回 `None`，避免刷日志/反复重试；
- 集合不存在时：
  - 用**租户 embedding** 实时探测维度（`app.state.vec_dim <= 0` 时 `aembed_query("dim-probe")`），支持启动时平台 embedding 不可用、或后来更换向量模型；
  - `create_collection(col, VectorParams(size=dim, distance=Distance.COSINE))`；
- 构建 `QdrantVectorStore(client, collection_name, embedding=tenant_emb)` 并缓存；
- 任何异常 → 记冷却时间、warning、返回 `None`（**降级为纯 LLM，不抛穿对话**）。

### 7.2 `get_tenant_retriever(app, tenant_id)`（第 111-122 行）

- `tenant_retrievers` 有缓存 → 返回；
- 没有 `tenant_store` → 返回 `None`（此时 `search_kb` 会回「知识库暂未就绪，请稍后再试。」）；
- 否则 `store.as_retriever(search_type="similarity", search_kwargs={"k": RETRIEVER_TOP_K})`（`RETRIEVER_TOP_K = 3`），缓存。

### 7.3 对话请求时何时准备

`get_tenant_agent(app, tenant_id)`（约第 425-460 行）每次构建/获取租户 Agent 时会调用：
```python
await ensure_tenant_vector(app, tenant_id)
get_tenant_retriever(app, tenant_id)
```
所以**对话一旦发生，就会懒创建租户集合与 retriever**，无需提前初始化。

### 7.4 Embedding / 对话模型来源（BYOK）

- 平台默认配置 = 平台管理员租户 `t_admin` 的模型配置（DB 单一数据源）；
- 租户可自定义（`use_custom`），配置缓存 300s，变更由 Go 调 `/agent/cache/clear` 并通过 Redis 广播各实例失效；
- `QDRANT_COLLECTION_NAME = "customer_service_knowledge"`（`config.py`）为历史遗留常量，**实际不再使用**，集合按 `kb_{tenant}` 命名（`db_ops.collection_name`）。

> 风险点：更换 embedding 模型/维度后，旧集合维度不匹配会导致写入/检索失败。处理方式：删除 `kb_{tenant}` 集合 + 对全部文档重索引。

## 8. 检索链路（对话中的 `search_kb`）

### 8.1 工具定义

`tools.py` 中 `search_kb(query)`，docstring 明确要求模型：工具返回「知识库暂未就绪」时如实告知，**不得编造价格/政策/库存**，建议稍后重试或转人工。默认系统 Prompt 也规定了「平台信息/课程内容/政策 → search_kb」。

### 8.2 执行流程（`tools.py` 第 57-94 行）

```
tenant_id ← tenant_var, thread_id ← thread_var
1. 进程内缓存命中？  → 直接返回（cache key = tenant + md5(query.lower().strip())，TTL 300s）
2. retriever = tenant_retrievers.get(tenant)
   None → "知识库暂未就绪，请稍后再试。"
3. docs = await retriever.ainvoke(query)
   异常 → warning + "知识库暂未就绪，请稍后再试。"（检索期降级，不抛穿对话）
4. docs 为空 → "未找到相关信息，建议转接人工客服。"
   非空     → "\n".join(f"- {doc.page_content}")
5. 落库 kb_hits（异步旁路，失败不影响回答）
6. 写缓存（TTL 300s）
```

### 8.3 命中落库（`_record_kb_hits`）

- 有命中：每个文档一行 `(tenant, thread, doc_id, title, query, score)`；
- 无命中：插入一行 `doc_id="" / doc_title="" / score=0`，用于统计「未命中查询」；
- 使用 `executemany`，异常只 warning。

> 注意：`score` 取 `doc.metadata.get("score", 0)`。QdrantVectorStore 默认 similarity 检索的返回文档 metadata 不一定带 `score`，因此实际可能大量为 0，做排序分析时需注意。

### 8.4 缓存与失效

| 缓存 | 位置 | TTL | 失效时机 |
|---|---|---|---|
| `tenant_stores` | `app.state` | 进程生命周期 | 无（重启/换模型时清） |
| `tenant_retrievers` | `app.state` | 进程生命周期 | 上传索引完成、删除、重索引、批量操作、`/kb/index` 后 `pop` |
| KB 检索结果 `_kb_cache` | 进程内存（`cache.py`） | 300s | 到期自动清理；**知识库变更不会主动清空**（最长可能读旧结果 5 分钟） |

> 多实例部署时这些缓存都是**进程内**的，只在处理请求的那个实例失效；其他实例最长要等 TTL（检索结果 5 分钟，retriever 需重启或下次命中另一实例时重建）。这是已知一致性弱点。

## 9. 后台管理能力

### 9.1 文档列表 `GET /agent/kb/documents`

参数：`category`（精确）、`keyword`（`title` 或 `file_name` ILIKE）、`order`、`page`（≥1）、`page_size`（1-100）。

排序：
| order | SQL |
|---|---|
| `created_desc`（默认） | `d.created_at DESC, d.id DESC` |
| `hit_desc` | `h.hit_count DESC NULLS LAST, d.created_at DESC` |
| `hit_asc` | `h.hit_count ASC NULLS FIRST, d.created_at DESC`（优先找从未命中的文档） |

返回每项：`doc_id, title, chunk_count, created_at, file_name, file_size, category, status, error_msg, updated_at, file_url, hit_count, last_hit_at`。
`file_url` 为空时按 `kb_file_url()` 兜底重建。

`hit_count/last_hit_at` 来自 `LEFT JOIN (SELECT doc_id, COUNT(*), MAX(hit_at) FROM kb_hits WHERE tenant_id=? GROUP BY doc_id)`。

### 9.2 分类 `GET /agent/kb/categories`

`GROUP BY COALESCE(NULLIF(category,''),'默认')`，按数量倒序，返回 `[{category, count}]`。

### 9.3 设置分类 `POST /agent/kb/documents/{doc_id}/category`

`{"category": "..."}`，`rowcount==0` → 404「文档不存在」。

### 9.4 删除 `DELETE /agent/kb/documents/{doc_id}`

顺序：
1. 查 `file_name`；
2. 删 Qdrant points（`doc_id` 过滤）；
3. 删 `kb_documents` 行；
4. 删共享卷原文件（尽力而为）；
5. 失效 retriever 缓存。

> Qdrant 删除即使失败也被忽略（`try/except`），避免存储故障阻塞 DB 清理。代价是可能残留孤儿向量，需人工清理。

### 9.5 平台设置

- `GET /agent/platform-settings`：列表，需 `X-Internal-Token`；
- `PUT /agent/platform-settings`：`{"key","value"}`；`kb_max_file_mb` 必须为 1-100 的整数。

| GET/POST | `/api/admin/platform-settings` | 平台管理员（内部 token 转发） |

### 10.2 租户隔离实现

- Go 代理到 Agent 时带 `X-Tenant-Id` 头；Agent 侧 `tenant_from_request()` 统一读取；
- 所有 DB 查询都带 `tenant_id = %s`；
- 所有 Qdrant 操作都用 `collection_name(tenant_id)`（物理隔离）；
- 原文件路径含租户目录（文件系统层面隔离）；
- 批量/索引接口先查归属再操作（防越权）。

> 风险点：Qdrant 集合名由 `tenant_id` 直接拼接（`kb_{tenant_id}`），若租户 ID 含特殊字符需保证命名合法；`/agent/*` 接口本身依赖内网隔离 + `X-Tenant-Id`，直接暴露公网时缺少鉴权。

## 12. 故障与降级矩阵

| 故障 | 表现 | 处理 |
|---|---|---|
| Redis 不可用 | 上传仍可（只是 DB 登记），`/kb/index` 入队失败 → `status=2`「Redis 索引队列不可用」 | Agent 启动因 `ping` 失败直接失败（fail-fast）；需恢复 Redis |
| Embedding 模型不可用 | 索引失败 `status=2`「向量模型/向量库不可用」；对话检索返回「知识库暂未就绪」 | 后台修复模型配置；`cache/clear` 后重试索引 |
| Qdrant 不可用 | `ensure_tenant_vector` 返回 None（60s 冷却），索引/检索降级 | 恢复 Qdrant 后等待冷却结束或重启 |
| 原文件缺失/解析失败 | `status=2`「原文件缺失或无法解析，请重新上传」 | 重新上传（同内容新 doc_id） |
| PDF 扫描件/图片型 | 上传 400「PDF 无可提取文本…暂不支持 OCR」 | 转文本后再上传 |
| 不支持格式 | 上传 400「暂不支持 .xxx 格式」 | 转换格式 |
| 文件过大 | 400「文件超过大小限制（N MB）」 | 压缩/拆分，或平台调大 `kb_max_file_mb` |
| 配额超限 | 429 文档数/容量达上限 | 删除旧文档 |
| 租户无集合/无文档 | 检索返回「知识库暂未就绪」或「未找到相关信息」 | 先索引文档；对话时会自动建集合 |
| 检索异常（如 key 错误） | warning 日志 `[KB Degrade]`，回答降级为纯 LLM 并如实告知 | 检查模型配置 |

**降级原则**：知识库不可用**不影响对话主流程**；`search_kb` 只返回明确话术，系统 Prompt 要求不得编造。

## 13. 运维与排查速查

### 13.1 常用 SQL

```sql
-- 某租户文档状态分布
SELECT status, count(*) FROM kb_documents WHERE tenant_id = 't1' GROUP BY status;

-- 待索引/失败文档（可再次触发 /kb/index）
SELECT doc_id, title, status, error_msg, updated_at
FROM kb_documents WHERE tenant_id = 't1' AND status IN (0, 2)
ORDER BY updated_at DESC;

-- 索引卡住（status=3）排查
SELECT doc_id, title, updated_at FROM kb_documents WHERE status = 3;

-- 文档命中排行（最近 7 天）
SELECT doc_id, doc_title, count(*) AS hits
FROM kb_hits
WHERE tenant_id = 't1' AND hit_at > now() - interval '7 days' AND doc_id <> ''
GROUP BY doc_id, doc_title ORDER BY hits DESC LIMIT 20;

-- 未命中查询（知识缺口）
SELECT query, count(*) AS miss
FROM kb_hits
WHERE tenant_id = 't1' AND doc_id = '' AND hit_at > now() - interval '30 days'
GROUP BY query ORDER BY miss DESC LIMIT 30;

-- 平台设置
SELECT key, value FROM platform_settings;
```

# 查看队头消息（不移除）

### 13.5 典型问题定位

| 现象 | 排查顺序 |
|---|---|
| 上传成功但对话查不到 | ① 看 `status`（是否为 0 未索引）→ ② 点「开始索引」→ ③ 看 `error_msg` → ④ 看 worker 日志 `KB worker indexed` → ⑤ 检查 `kb_{tenant}` points_count |
| 索引一直「索引中」 | worker 是否在跑（`KB index workers started`）、Redis 队列是否积压、embedding 是否超时 |
| 重索引后仍返回旧内容 | 检查 `_kb_cache` 300s 缓存；等待 TTL 或多实例重启 |
| 下载 404 | 共享卷未挂载/文件被删；检查 `file_url` 与磁盘文件是否一致 |
| 列表看不到命中数 | `kb_hits` 是否有数据；`search_kb` 是否真正走检索（缓存命中不落库） |

> 注意：**缓存命中的检索不会写 `kb_hits`**（代码在缓存命中时直接 return）。因此命中统计低估高频重复问题，符合「按真实检索压力统计」的口径，但分析时需知晓。

## 14. 已知风险与改进建议（供后续迭代）

1. **KB 检索缓存不随知识库变更失效**：`_kb_cache` TTL 300s，索引/删除/重索引后可能读到旧答案。建议在 `routers_kb` 变更操作里同时清理该租户相关缓存（需要按 tenant 前缀遍历），或改用 Redis 缓存并带版本号。
2. **批量删除不删原文件**：`/kb/batch` 的 `delete` 只删 DB 与 Qdrant，共享卷会残留文件；建议补 `delete_kb_file`。
3. **Qdrant 集合无租户校验**：`collection_name()` 直接拼接 `tenant_id`，`/agent/*` 仅靠内网 + 头信任；建议校验租户 ID 字符集并对 `/agent/*` 加 `X-Internal-Token` 统一校验。
4. **`kb_hits.score` 大量为 0**：Qdrant similarity 检索 metadata 无 score；建议改用 `similarity_search_with_score` 或记录 rank 作为辅助指标。
5. **重索引期间旧内容不可用**：`/reindex` 先删旧向量再入队，索引完成前该文档检索不到。若需「零停机切流」，可改为双集合或先写新 points 再删旧。
6. **`requeue_pending` 只处理 status=3**：如果 worker 在 status=0 入队后被 kill，队列消息在 Redis 中仍在，会随消费恢复；但若 Redis 数据丢失，status=0 文档不会自动重建，需要用户手动索引（设计如此）。
7. **Qdrant 删除失败被吞**：可能留下孤儿向量，长期运行建议周期性对账（DB 中 doc_id 与 Qdrant payload 对账清理）。
8. **依赖缺失提示依赖懒加载**：`kb_parser` 在缺少 `pypdf/python-docx/openpyxl` 时抛 RuntimeError，部署镜像需确保这些依赖已安装（requirements 与 Docker 镜像需一致）。
9. **单文档 100 万字上限**：超过部分被静默截断（`content[:MAX_TEXT_CHARS]`），超长文档建议拆分为多个文档上传，并在上传端提示。
10. **默认 Prompt 与工具命名耦合**：系统 Prompt 明确写 `search_kb`，若改名工具需同步改 Prompt。
